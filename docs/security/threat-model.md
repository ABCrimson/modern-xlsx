# Threat model

This page describes how modern-xlsx defends itself against hostile input, as the code in this repository does it, and which test proves each defence. It names functions, constants and tests rather than line numbers, so it stays true while the files move. The crate versions in use are the ones in `Cargo.lock`.

To report a vulnerability, see [SECURITY.md](../../SECURITY.md).

## Scope and trust boundary

The untrusted input is the bytes passed to `readBuffer` (or read from disk by `readFile`) and the password passed with them. Everything else, including the `ReadOptions.limits` the caller chooses and the workbooks the caller builds for writing, comes from the application and is trusted.

- The reader is the Rust core compiled to WebAssembly. It parses the bytes it is given and nothing else: neither `crates/modern-xlsx-core/src` nor `crates/modern-xlsx-wasm/src` contains file-system or network code.
- `readFile` reads the one path it is given through `readFileBytes` in `packages/modern-xlsx/src/runtime-node.ts`, in Node.js-compatible runtimes. In browsers and workers the twin in `packages/modern-xlsx/src/runtime-browser.ts` throws `IO_ERROR` instead.
- Relationship targets in a file, such as hyperlinks and external workbook links (`external_reference_paths` in `crates/modern-xlsx-core/src/reader.rs`), are kept as strings and never fetched.
- A part that relationships of one type name (comments, threaded comments, tables, drawings, charts, slicers, timelines, and the pivot table, pivot cache definition, pivot cache records, slicer cache and timeline cache parts) is parsed at most once per read and enters the model for the first owner naming it (`PartLedger` in `crates/modern-xlsx-core/src/reader.rs`): the same or a later sheet, drawing, pivot cache definition or the workbook naming it again is skipped and counted in one aggregated warning per kind. Two `<sheet>` rows of `xl/workbook.xml` that resolve to one worksheet part fail the read with `SECURITY`.
- A rejected read throws a `ModernXlsxError` with a code, among them `SECURITY` for hostile structure, `SIZE_LIMIT` for a hard size cap, `PASSWORD_PROTECTED` for a password or encryption problem, `UNRECOGNIZED_FORMAT` and `LEGACY_FORMAT` for input that is not an XLSX package.

## Format detection

`detect_format` in `crates/modern-xlsx-core/src/ole2/detect.rs` looks only at the leading magic bytes: the 8-byte OLE2 signature (`OLE2_MAGIC`) or the ZIP local-header signature (`ZIP_MAGIC`). Anything else is `UNRECOGNIZED_FORMAT`. `classify_ole2` then names an OLE2 file an encrypted package (`EncryptionInfo` and `EncryptedPackage` streams), a legacy `.xls` (`LEGACY_FORMAT`) or an unknown compound file (`UNRECOGNIZED_FORMAT`).

Detection and the OLE2 reader are built in every build, including the lite build (`modern-xlsx/lite`), which is compiled without the `encryption` feature. The lite build reports an encrypted file as `PASSWORD_PROTECTED` even when a password is given (a hostile `EncryptionInfo`, such as a `spinCount` above `MAX_SPIN_COUNT`, is `SECURITY` there as in the full build), and its `readBuffer` rejects `options.password` with `INVALID_ARGUMENT` before calling WASM.

Tests: `crates/modern-xlsx-core/tests/lite_detection.rs`, run with `cargo test -p modern-xlsx-core --no-default-features`.

## ZIP archives

`read_zip_entries` in `crates/modern-xlsx-core/src/zip/reader.rs` opens the package and runs these checks on every read (its `# Security` doc section lists the name, duplicate, count and inflate checks):

- An entry name that could escape the archive root is `SECURITY` (`is_unsafe_entry_name`): a NUL byte, a leading `/` or `\`, a `..` component split on both separators, or a drive prefix such as `C:` at the start. A colon later in the name is legal in OPC part names and is accepted.
- Duplicate names are `SECURITY`: byte-identical names in the central directory (`has_duplicate_names`, checked before iteration because the `zip` crate collapses them), and names that decode to the same string.
- More entries than `max_entries` is `SECURITY`.
- An entry with a compressed size of 0 and a non-zero declared size is `SECURITY`.
- Each entry inflates through a reader capped at min(what is left of `max_decompressed_size`, compressed size × `max_compression_ratio`) + 1 bytes. An entry that reaches the cap is `SECURITY`, for its ratio or for the total budget, so a decompression bomb is cut off while it inflates and never inflated in full.
- The declared size in the central directory is attacker-controlled (a forged ZIP64 field can claim `u64::MAX`), so it is only a capacity hint, held to the entry's cap and to `MAX_CAPACITY_HINT`, 64 MiB (67,108,864 bytes). The buffer grows as the entry really inflates.

The limits are `ZipSecurityLimits`:

| Field (`ReadLimits` key)                        | Default                     | Ceiling                                                                                           |
| ----------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------- |
| `max_decompressed_size` (`maxDecompressedSize`) | 2 GiB (2,147,483,648 bytes) | `MAX_DECOMPRESSED_SIZE_CEILING`, 2 GiB (2,147,483,648 bytes)                                      |
| `max_compression_ratio` (`maxCompressionRatio`) | 100                         | none                                                                                              |
| `max_entries` (`maxEntries`)                    | 100,000                     | `MAX_ENTRIES_CEILING`, 1,048,576                                                                  |
| `max_json_length` (`maxJsonLength`)             | 536,870,888 bytes           | `MAX_JSON_LENGTH_CEILING`, 536,870,888 bytes (V8's maximum string length, 24 bytes under 512 MiB) |

The defaults come from the `Default` implementation of `ZipSecurityLimits`. `ZipSecurityLimits::clamped` holds each value to its ceiling and resets a NaN or non-positive ratio to the default. In JavaScript the limits are `ReadOptions.limits`: `serializeReadLimits` in `packages/modern-xlsx/src/read-limits.ts` rejects an unknown key, or a value that is not a finite number above zero (and, for the three counts, a safe integer), with `INVALID_ARGUMENT`. The WASM bridge (`parse_limits` in `crates/modern-xlsx-wasm/src/lib.rs`) deserializes the object with unknown keys denied and applies `clamped`, so a value above a ceiling is lowered, not rejected.

An application that reads uploads from strangers can tighten the limits:

```ts
import { readFile } from 'node:fs/promises';
import { initWasm, ModernXlsxError, readBuffer, SECURITY, SIZE_LIMIT } from 'modern-xlsx';

await initWasm();
const bytes = await readFile('upload.xlsx');

const MiB = 1024 * 1024;
const limits = {
  maxDecompressedSize: 256 * MiB, // default and ceiling: 2 GiB
  maxCompressionRatio: 100, // the default; no ceiling
  maxEntries: 10_000, // default 100,000; ceiling 1,048,576
  maxJsonLength: 128 * MiB, // default and ceiling: 536,870,888 bytes
};

try {
  const wb = await readBuffer(bytes, { limits });
  console.log(wb.sheetNames);
} catch (err) {
  if (err instanceof ModernXlsxError && (err.code === SECURITY || err.code === SIZE_LIMIT)) {
    console.error(`rejected: ${err.message}`);
  } else {
    throw err;
  }
}
```

- `crates/modern-xlsx-core/tests/hostile_inputs.rs`: `zip_name_cases` (eight unsafe names, a duplicate name, a legal colon, a missing `xl/workbook.xml`), `zip_bomb_case` (64 MiB of zeros against a 1 MiB budget with an unbounded ratio) and `forged_central_directory_size_case` (declared sizes `0x80000000` and `0xFFFFFFFE`), all run by `hostile_inputs_end_in_exact_codes_within_bounds`. The cases run under a one-second bound, except the duplicate-name, colon and missing-part checks, and a counting allocator (`peak_alloc`) bounds the peak heap: under 8 MiB for the zero bomb and under 64 MiB for each forged size.
- `packages/modern-xlsx/__tests__/hostile-input.test.ts`, 'hostile ZIP archives': seven of the unsafe names, a duplicate name, a 64 MiB zero bomb at the default limits, the missing parts and both forged sizes through the WASM build, where each must give its code and never a WASM trap.
- `packages/modern-xlsx/__tests__/read-limits.test.ts`: each limit applied, clamped above its ceiling and validated by `serializeReadLimits`.

## Output size

The reader returns the workbook to JavaScript as one JSON string. `check_json_len` in `crates/modern-xlsx-core/src/reader.rs` runs after every worksheet row (`JsonSink::end_row`), after each sheet and once at the end, and fails with `SIZE_LIMIT` as soon as the JSON is longer than `max_json_length`, so a read fails cleanly instead of exceeding V8's string limit. The length is counted in UTF-8 bytes, an upper bound on UTF-16 units, so a workbook with non-ASCII text can be rejected slightly before V8's own limit. The JSON buffer's first reservation is 15 times the input, held between 4 KiB and `JSON_PREALLOC_CAP`, 64 MiB (67,108,864 bytes).

Tests: `packages/modern-xlsx/__tests__/read-limits.test.ts` ('rejects with SIZE_LIMIT when the JSON exceeds maxJsonLength', 'enforces maxJsonLength on the password path').

Shared text amplification. A workbook can store a string once and name it from many places: a shared string from every `t="s"` cell, a comment author from every note, an external hyperlink relationship from every `<hyperlink r:id>`, and a namespace the `<worksheet>` root declares once from every kept worksheet extension (`<extLst><ext>`) that uses its prefix, since each kept extension is made self-contained. The read copies the string into each place, so a file a few dozen KB long, inside every ZIP limit (size, ratio, entries), can expand to gigabytes: a 77 KB file with one 100,000-character shared string in 10,000 cells built a 964 MiB model, and a 68 KB file with one 100,000-character author on 10,000 notes peaked at 3.8 GiB. Each read keeps one running count of the bytes it copies this way (`ExpansionBudget` in `crates/modern-xlsx-core/src/ooxml/shared_strings.rs`, spent before each copy by `resolve_sst`, `parse_comments_within` and `parse_hyperlink_attrs`, and for each extension's copied declarations by `kept_ext` in `crates/modern-xlsx-core/src/ooxml/worksheet/driver.rs`) and fails with `SIZE_LIMIT` once the count passes `max_json_length`, on both read paths (`read_xlsx*` and `read_xlsx_json*`). Nothing that read before is refused for the text it copies: the JSON a read returns holds every counted copy at no less than its byte length, so a read whose count passes `max_json_length` could not have returned its JSON (the memory of worksheet lists, below, is counted against the same limit and can refuse a workbook whose JSON fits). On the JSON path (`read_xlsx_json*`, which the WASM build and the npm package use) a copy is written escaped, up to 6 bytes per byte counted, so the JSON is also checked after each shared string a cell's `<v>` names and each cell, comment, hyperlink, kept extension and workbook field, and the buffer's last growth is clamped to the limit plus 8 MiB; the JSON passes the limit by at most the item written last. Memory is therefore bounded by the counted copies the parsed parts hold (up to the limit: comment authors in comments, hyperlink targets in hyperlinks), plus the JSON buffer (up to the limit plus 8 MiB, and the old buffer while it grows), plus the parts: about three times the limit at worst for the copied text (about 1.5 GiB by default), plus up to the limit again for the records a read keeps in its defined names, shared strings, styles part, charts, threaded comments and worksheet lists (see One cell and worksheet lists, and Styles and the other parts). Measured worst case: a 73 KB file with one 40,000-control-character comment author on 12,000 comments peaked at 1,247 MiB natively; shared strings, which are not copied outside the JSON, peaked at 0.8-0.92 GiB (one cell with 13,000 `<v>` naming one 40,000-control-character string: 911 MiB). Each such file fails in about 0.25-0.6 seconds natively (measured 2026-11-12, Windows 11 x64, release profile; the slowest is the 12,000-comment file, 0.59 s). The Rust model API (`read_xlsx` and its variants, not part of the npm package) clones a rich shared string's runs into every cell naming it and counts each run at its JSON floor (11 bytes plus its text), though a run costs `size_of::<RichTextRun>()` = 248 bytes plus its heap: a rich entry of 10,000 one-letter runs in 50,000 cells peaked at 923 MiB against a 50 MB limit (about 19x), so its peak can reach about 19x `max_json_length`. Copies that never reach the result are given back when their part ends: a comments part that fails to parse (it is preserved verbatim, its notes dropped) and a last row cut off by the end of its worksheet part. A kept worksheet `<ext>` costs its own length plus, for each prefix it uses, a search of the declarations in scope inside it (those of the element itself, sorted, then those of its open ancestors, in an ordered map, a B-tree) and, when none binds it, one binary search of the `<extLst>`'s and the root's declarations: an inserted declaration is a copy of text rendered once per part root (`RootNamespaces` in `crates/modern-xlsx-core/src/ooxml/xml.rs`), and `kept_ext` counts the inserted bytes against `max_json_length` before it builds the kept string. None of these lookups goes through a hasher, and neither does the test of a hyperlink's `r:id` prefix against the prefixes the root binds to the relationships namespace (a sorted list in `crates/modern-xlsx-core/src/ooxml/worksheet/driver.rs`, searched by `parse_hyperlink_attrs`), so no choice of prefixes makes them collide; on this path the standard library's hasher, whose keys are not secret in the WebAssembly build, is keyed by no prefix a file chooses (read from the code on 2026-11-14). Natively (release profile, 2026-11-13) an inserted declaration costs about 77 ns on the model path and 104 ns on the JSON path, which also writes it into the JSON (about 210 to 230 ns in an earlier 1.3.0 development build). Through the release WebAssembly build, the worst package under 2 MB found (2026-11-13: the root declares 100, 1,000 or 5,000 prefixes used by each of as many `<ext>` as fit in 2 MB, or 1,000 prefixes bound to 2,000-character URIs) reads in 3.90 to 4.35 s (1,000 prefixes x 11,500 `<ext>` in 1,965,760 bytes, 343 MB of JSON, four runs; 5.24 to 5.45 s in an earlier 1.3.0 development build; 3.43 to 3.52 s for the same `<ext>` elements declaring their prefixes themselves); the JSON length check bounds it, since every inserted declaration is counted against `maxJsonLength`, and the long-URI form ends in `SIZE_LIMIT` in 0.43 s. Through the WebAssembly build much of that time is the growth of its memory, which costs more in an instance whose memory has already grown (see Known limitations: The WebAssembly memory grows in small steps).

Tests: `shared_text_expansion_ends_in_size_limit_within_bounds` in `crates/modern-xlsx-core/tests/hostile_read.rs` (the shared-string, author and hyperlink shapes at 10,000 and 30,000 copies fail on both read paths within the time and peak-heap bounds; a workbook under the budget reads with the same JSON; a lower limit is honoured); 'rejects with SIZE_LIMIT when one shared string expands past maxJsonLength' and 'rejects with SIZE_LIMIT when one comment author expands past maxJsonLength' in `packages/modern-xlsx/__tests__/read-limits.test.ts`.

One cell and worksheet lists. The worksheet driver (`crates/modern-xlsx-core/src/ooxml/worksheet/driver.rs`) hands each child of a cell (`<f>`, `<v>`, `<is>`) to the sink as it ends, so an open cell holds its attributes, one formula state and the text of the open child, whatever its number of children: the model path keeps one value, formula, inline string and merged formula state per cell, and the JSON path writes each child and checks the limit after it. One cell of 25,000,000 `<f/>` (a 1.7 MB file) reads in 192 MiB natively and 195 MiB of WebAssembly memory. Each element a worksheet list keeps (columns, merged ranges, hyperlinks, page breaks, `cfvo`s, colour-scale colours, filter values, custom filters, filter columns, pane selections, data validations, conditional-format rules, conditional formats, sparklines, sparkline groups, kept extensions and root namespace declarations) is charged before it is kept, at the `size_of` of its record plus the heap bytes of its strings, to a second count of the same `ExpansionBudget` (`stored`, held to `max_json_length`, one per read and shared by all its sheets; with the `parallel` Cargo feature, per sheet); a copy already counted as shared text is not counted again, and `JsonSink::finish` writes each list one element at a time, the page breaks, the auto filter's columns, values and custom filters, and the tables included, checking the JSON length after each; one element (a table with its columns, a conditional format with its rules) is serialized whole. Outside the sheet's own keys, `push_field` and `inject_field` in `crates/modern-xlsx-core/src/reader.rs` serialize each workbook-level field and each sheet's charts, pivot tables, threaded comments, slicers and timelines whole, as one temporary string beside the JSON, and check the length after it; each is bounded by its part's decompressed size times its parser's factor (below), and a field of control characters, which takes 6 bytes of JSON per byte of XML, still traps the WebAssembly build (see Styles and the other parts). Before that, 15,000,000 page breaks (a 9.4 MB package whose records fit the list count) were serialized into one temporary string of about 570 MB beside the output and aborted the WebAssembly instance; they now end in `SIZE_LIMIT` on the JSON path at 2,440 MiB natively (3,039 MiB with the breaks serialized whole), measured on 2026-11-13. The charge is the in-memory size on the target, and wasm32 records are about half their x86_64 size while strings cost the same on both, so the WebAssembly build keeps 1.5 to 1.9 times as many elements before `SIZE_LIMIT` (1.68 times for one-rule conditional formats, 1.88 for list data validations, 1.65 for hyperlinks and 1.45 for merged ranges, from the stored bytes each needs on the two targets). At the default limit, on a 1.3.0 development build of 2026-11-13, the first count refused is 1,084,375 one-rule conditional formats, 1,849,609 list data validations, 3,921,875 hyperlinks and 13,839,843 merged ranges natively, and between 1,750,000 and 1,900,000 one-rule conditional formats and between 3,350,000 and 3,600,000 list data validations in the WebAssembly build. A list that ends in `SIZE_LIMIT` peaks at its records up to the limit, the vector's last doubling and the part, about three times the limit (1,601 MiB was the highest measured natively): 9,000,000 `<cfRule/>` in one conditional format (a 1.4 MB file) end in `SIZE_LIMIT` at 1,396 MiB natively and 2,055 MiB of WebAssembly memory, where 1.2.1 read the file at 3,943 MiB. Real sheets stay inside the default: 1,000,000 one-rule conditional formats use 92.4% of it natively and 55.1% in the WebAssembly build, and 1,000,000 list data validations 54.2% and 28.9%. The rows and cells of the model path are not charged; the workbook's defined names are (see Styles and the other parts). These figures were measured on 2026-11-13 (a UTC date): native ones with the release profile on `nightly-2026-11-13`, WebAssembly ones with the release module under Node v26.13.0.

Tests: `element_flood_cases` and `real_list_cases`, run by `shared_text_expansion_ends_in_size_limit_within_bounds` in `crates/modern-xlsx-core/tests/hostile_read.rs` (one cell of 25,000,000 `<f/>`, 12,500,000 `<v>`, 8,000,000 `<is>` or 8,000,000 `<f>x</f>` reads within the peak bounds; 9,000,000 `<cfRule/>`, `<dataValidation/>` or `<selection/>` and 5,000,000 `<hyperlink/>` end in `SIZE_LIMIT` within `FLOOD_LIMIT` and `LIST_PEAK_LIMIT`; 1,000,000 list data validations, one-rule conditional formats, hyperlinks or merged ranges read at the default limit; a debug build runs a tenth of each flood against a tenth of the limit); `sink_list_cases` in the same file (15,000,000 `<brk/>` in `<rowBreaks>` and in `<colBreaks>` end in `SIZE_LIMIT` on the JSON path within `BREAK_FLOOD_LIMIT` and `BREAK_PEAK_LIMIT`; 3,000,000 filter columns, 9,000,000 filter values and 6,000,000 custom filters read within the flood bounds); `sheet_lists_fail_at_the_limit` and `auto_filter_matches_serde_json` in `crates/modern-xlsx-core/src/ooxml/worksheet/sink_json.rs`.

Styles and the other parts. The styles parser (`Styles::parse_within` in `crates/modern-xlsx-core/src/ooxml/styles.rs`) keeps every number format, font, fill, gradient stop, border, cell format, named cell style and differential format it meets, and each tag a differential font lists as explicitly off. An empty record is 5 to 12 bytes of XML (`<xf/>` to `<cellStyle/>`) and up to 1,200 bytes of memory (an empty `<dxf/>` on a 64-bit target, 784 bytes on wasm32), so without a charge a 295,241-byte package of 3,300,000 `<dxf/>` took 7,219 MiB natively and trapped the WebAssembly build at 3,158 MiB, where 1.2.1, whose style records are smaller, read it in 25 MiB. `parse_common` in `crates/modern-xlsx-core/src/reader.rs` now makes the read's one `ExpansionBudget` before `xl/workbook.xml` is parsed, and every style record is charged to its `stored` count before it is kept, at the `size_of` of its record plus the heap bytes of its strings, after the defined names and the shared strings and ahead of the charts, the threaded comments, the comments and the worksheet lists of the same read; with the `parallel` Cargo feature the records counted before the sheets and each sheet's list memory are held to the limit together. A read past the limit fails with `SIZE_LIMIT` ("the defined names, shared strings, styles, chart series and axes, threaded comments and worksheet lists take more memory than the N-byte limit"). The tightest list is differential formats: at the default limit the 447,393rd empty `<dxf/>` is refused natively and the 684,785th in the WebAssembly build, computed from the record sizes (border 945,196 and 1,458,889; fill 2,033,602 and 3,050,403; font 2,164,802 and 3,355,444; cell format 4,473,925 and 5,835,554). Measured after the change: 3,300,000 `<dxf/>` end in `SIZE_LIMIT` at 919 MiB natively (0.28 s) and 1,590 MiB of WebAssembly memory, `<dxf></dxf>` in a 551,810-byte package at 936 MiB and 1,606 MiB, 6,000,000 `<border/>` at 905 MiB and 1,528 MiB, and 9,000,000 `<fill/>` at 854 MiB and 1,472 MiB; every styles flood ends in under 1.5 s natively, below `LIST_PEAK_LIMIT` (1,792 MiB). A generous real styles part (64,000 cell formats, 10,000 fonts, fills, borders and differential formats, 2,000 number formats) uses about 33 MB natively and 23 MB in WebAssembly, 6% and 4% of the default limit, and reads at the same speed as before. Still bounded only by the size of the part: the verbatim `<tableStyles>`, `<colors>` and root `<extLst>` strings (each at most its own XML plus the inherited namespace declarations it uses; a repeated element replaces the earlier one), the root's namespace list while the part is parsed (about 4.5 times its XML), a vector's spare capacity after doubling, and the allocator overhead of tiny strings. The root's namespace declarations are indexed once per part (`RootNamespaces` in `crates/modern-xlsx-core/src/ooxml/xml.rs`, built where the styles parser, the worksheet driver and the pivot cache definition parser read the root), and `self_contained_fragment` looks up only the prefixes a verbatim element uses and does not declare, so each kept element (a styles `<colors>`, `<tableStyles>` or `<extLst>`, a worksheet `<ext>`, a pivot `<cacheSource>`) costs its own length plus those prefixes. Before, each element rebuilt a map of every declaration, so read time was linear in declarations times elements, at 11.7 to 48 ns per pair natively: 50,000 declarations and 20,000 `<colors/>` (a 198,621-byte package) took 35 s natively and 17.9 s in the WebAssembly build, and 50,000 declarations and 2,000,000 elements projected to over an hour; they now take 13 to 17 ms on each read path natively. A repeated verbatim element is only range and UTF-8 checked, and the last one of a part is made self-contained once, so a long root URI is no longer copied once per repeat (50,000 `<colors>` under a 400,000-byte URI: 29 s before, 0.12 s in an unoptimized build after). These figures were measured on 2026-11-13.

The shared strings parser (`SharedStringTable::parse_within` in `crates/modern-xlsx-core/src/ooxml/shared_strings.rs`) kept up to 78.0 times its XML (one `<si>` of empty `<r></r>` runs, 248 bytes per 7-byte run natively) with no bound but the 4 GiB WebAssembly memory, so one entry of 10,000,000 runs (an 820,932-byte package) trapped the WebAssembly build at 2,675 MiB. Every entry is now charged at the `size_of` of its record, and every rich text run at the `size_of` of its record plus its strings, before it is kept; the text of a plain entry is not charged: it is bounded by the part size (one byte per byte of XML) and the JSON length check. That file now ends in `SIZE_LIMIT` natively in 0.5 s at a 1,618 MiB peak and through the WebAssembly build in 535 ms. These figures were measured on 2026-11-13.

Every part parser was also called alone on 20 MB of XML of its smallest repeated element, natively (peak heap over XML bytes): shared strings 78.0 (one `<si>` of `<r></r>`), charts 60.4 (`<ser></ser>`, `<ser><idx/></ser>`, `<ser><tx/></ser>`) and 34.0 (`<catAx></catAx>`, `<valAx></valAx>`), defined names 34.0 (`<definedName/>`) and 17.0 (with `name="a"`), threaded comments 27.7, table columns 23.9, pivot cache fields 23.9, pivot shared items 20.1 (`<s/>`, `<m/>`), slicers 17.7, persons 15.2 (`<person id="a"/>`), pivot fields 12.6, pivot items 10.1, timelines 8.2, slicer cache items 6.3, comments 5.7 and drawing anchors 2.7; content types, document properties, the theme and timeline caches keep no list that grows, and VML drawings, external links, metadata and custom XML are kept as bytes. Charged to the read's `stored` count, and so held to `max_json_length` together with the styles and the sheets: shared strings, style records, worksheet lists, chart series and axes (`ChartData::parse_within` in `crates/modern-xlsx-core/src/ooxml/charts/parser.rs`), threaded comments and their mentions (`parse_threaded_comments_within`) and defined names (`WorkbookXml::parse_within`); a drawing that contributes no chart and a threaded comments part that does not parse give back what they counted. Bounded only by their part's decompressed size, which the ZIP limits hold, times their factor: tables, pivot cache definitions and pivot tables, persons, slicers and slicer caches, timelines, drawing anchors, comments (their author copies are charged as shared text) and the workbook's other lists (sheets, views). Through the WebAssembly build, with each package padded to a compression ratio of 74 to 91 (a random comment of a 74th of the part), the smallest trapping package was a chart of 94 MB of `<ser></ser>` (1,131,472 bytes) both in 1.3.0 before the charge and in 1.2.1 (it now ends in `SIZE_LIMIT`); a pivot cache of 175 MB of `<s/>` shared items (1,932,022 bytes; `SIZE_LIMIT` from 100 MB) in 1.3.0 and of 131 MB (1,447,618 bytes) in 1.2.1; and 173 MB of drawing anchors (2,323,976 bytes) in 1.3.0 and 81 MB (1,092,556 bytes) in 1.2.1. Table columns, pivot cache fields, pivot fields and items, persons, comments, slicers, slicer items and timelines read 200 MB of XML (2.2 to 2.6 MB packages) in both. A field serialized whole (see One cell and worksheet lists) made of control characters, 6 bytes of JSON per byte of XML, still traps both builds: a number format code from 180 MB of XML (1,868,971 bytes; `SIZE_LIMIT` from 100 to 179 MB) in 1.3.0 and from 158 MB (1,640,821 bytes) in 1.2.1, a defined name's value from 180 MB (1,869,023 bytes) in 1.3.0 and 158 MB (1,640,878 bytes) in 1.2.1, and one shared string from 195 MB (2,024,414 bytes) in 1.3.0 and 90 MB (935,635 bytes) in 1.2.1. These figures were measured on 2026-11-13 with the release profile (native peaks by `peak_alloc`) and the release WebAssembly module under Node v26.13.0; the struct sizes are `size_of` on `x86_64-pc-windows-msvc` and `-Zprint-type-sizes` on `wasm32-unknown-unknown`. The writer also bounds what it generates from a small model. One write generates at most `MAX_GENERATED_NOTE_SHAPES` notes, 131,072 (`crates/modern-xlsx-core/src/ooxml/vml.rs`): a VML note shape added for a legacy comment, in a generated drawing or merged into a preserved one (about 640 bytes), and a `tc=` placeholder comment added for a thread root (about 430 bytes, counted once with the shape it gets). A preserved drawing written as it is counts nothing, so a workbook Excel saved is written back whatever its number of notes. At the ceiling a write takes about 0.5 seconds and a 243 MiB peak heap natively, and 0.7 seconds and 338 MiB of linear memory in the WASM build. The ceiling is the largest power of two whose output reads back: a read keeps the generated note drawing as a preserved entry, which the read JSON carries as an array of byte values, so a package with more than about 207,000 generated notes fails to read with `SIZE_LIMIT` at `max_json_length` (536,870,888 bytes, its default and ceiling). The pivot ceilings `MAX_FIELD_ITEMS` and `MAX_ADDED_ITEMS` in `crates/modern-xlsx-core/src/ooxml/pivot_table.rs` fail the same way. The streaming writer writes no comments.

Tests: `many_thread_roots_without_notes_case` and `many_legacy_notes_without_a_drawing_case` in `crates/modern-xlsx-core/tests/hostile_inputs.rs` (1,000,000 each, `SIZE_LIMIT` within one second and under 16 MiB of peak heap); `exactly_the_ceiling_of_generated_notes_writes_and_one_more_fails`, `a_preserved_note_drawing_matching_its_notes_writes_past_the_ceiling` and `generated_notes_are_counted_per_write_across_sheets` in `crates/modern-xlsx-core/src/writer/tests.rs`; 'rejects toBuffer() with SIZE_LIMIT for one note past the ceiling' in `packages/modern-xlsx/__tests__/note-ceiling.test.ts`.

Times and memory figures on this page were measured on 2026-11-12 on a Windows 11 laptop with an Intel Core Ultra 9 290HX Plus: native figures with release builds of the Rust core (peak heap by a counting allocator), WASM figures with the release WebAssembly build under Node v26.13.0, unless a line says otherwise. ## XML

The parts are parsed with `quick-xml` as a stream of events, never as a tree and never with DTD processing.

- In text, `push_general_ref` in `crates/modern-xlsx-core/src/ooxml/xml.rs` resolves character references and the five predefined entities (`&amp;`, `&lt;`, `&gt;`, `&quot;`, `&apos;`). Any other named entity is dropped and the surrounding text kept, because OOXML parts declare none. A malformed character reference is `XML_PARSE`.
- In attributes, `attr_str` resolves the same set; an undeclared entity is `XML_PARSE`.
- A pivot cache source that is not a worksheet is kept as its raw `<cacheSource>` span and written back as read, so `check_kept_refs` in `crates/modern-xlsx-core/src/ooxml/pivot_table.rs` checks that span when it is kept: every attribute value through `attr_str`, and every reference in text through `push_general_ref`, refusing too a named entity other than the five predefined ones. Such a span is `XML_PARSE`, and the cache definition is then an optional part that failed to parse (below), so a span is never written with a reference to a DTD entity its part no longer declares.
- A DOCTYPE is skipped: no parser acts on it, so an internal subset is never expanded and an external entity is never resolved.
- A part that fails to parse is handled by `optional_part` in `crates/modern-xlsx-core/src/reader.rs` when the part is optional: the reader logs it and keeps the part's bytes unparsed, and a `SECURITY` error stays fatal. A required part such as `xl/workbook.xml` fails the read.

Tests: `doctype_case` in `crates/modern-xlsx-core/tests/hostile_inputs.rs` (nested internal entities and a `SYSTEM` entity in a worksheet and in the shared-string table read as empty cells); 'a DOCTYPE with internal and external entities is never expanded or resolved' in `packages/modern-xlsx/__tests__/hostile-input.test.ts`; `push_general_ref_drops_unknown_named_entities`, `push_general_ref_rejects_malformed_char_refs` and `attr_str_rejects_unknown_entities_naming_the_key` in `crates/modern-xlsx-core/src/ooxml/xml.rs`; and the per-parser tests `bad_entity_is_xml_parse_error` (slicers, timelines, threaded comments), `bad_entity_in_attribute_is_xml_parse_error` (tables) and `bad_entity_in_ref_is_xml_parse_error` (comments).

## OLE2 compound files

An encrypted workbook is an OLE2 (MS-CFB) compound file. The MS-CFB reader in `crates/modern-xlsx-core/src/ole2/cfb/reader.rs` treats every header field and sector ID as hostile:

- The header must carry the byte order mark `FE FF`, major version 3 with sector shift 9 or version 4 with shift 12, mini sector shift 6 and mini stream cutoff 4096; anything else is `UNRECOGNIZED_FORMAT`.
- `collect_fat_sectors` gathers the FAT sector list from the 109 header slots and the DIFAT chain. The list is capped at the number of sectors the data can hold, the DIFAT walk stops at a revisited sector, and a FAT sector listed twice is `SECURITY`.
- `follow_chain` walks a FAT or MiniFAT chain with a visited bitmap; a sector seen twice is a loop and `SECURITY`. Sector offsets saturate (`sector_offset`), so a huge sector ID on 32-bit WASM reads nothing instead of overflowing.
- Buffers are sized from the bytes present, never from header counts: `read_sectors` reserves at most the file's length.
- `declared_size` compares a stream's declared size with the bytes its chain holds; a larger declaration is `SECURITY`.
- `read_mini_stream` applies the same chain and size checks to the MiniFAT, the mini-stream container and the stream inside it.

Tests in `crates/modern-xlsx-core/src/ole2/cfb/reader.rs`: `self_looping_directory_is_a_security_error`, `mini_chain_loop_is_a_security_error`, `self_looping_difat_chain_terminates`, `repeated_header_fat_sector_is_rejected`, `fat_sector_repeated_in_difat_is_rejected`, `v4_entry_size_u64_max_is_a_security_error`, `invalid_headers_are_unrecognized_format` and `chain_past_end_of_file_reserves_at_most_the_file`. `ole2_cases` in `crates/modern-xlsx-core/tests/hostile_inputs.rs` adds directory sizes `0xFFFFFFFF` (v3) and `u64::MAX` (v4), a Standard `headerSize` of `0xFFFFFFFC` and a self-looping directory chain, each under one second and 64 MiB of peak heap; 'hostile OLE2 compound files' in `packages/modern-xlsx/__tests__/hostile-input.test.ts` repeats them through WASM. `read_xlsx_does_not_panic_on_malformed_ole2_directory` in `crates/modern-xlsx-core/tests/security_tests.rs` covers a malformed directory.

The OLE2 writer, `write_ole2` in `crates/modern-xlsx-core/src/ole2/cfb/writer.rs`, lays out version 3 files with a MiniFAT for streams under 4096 bytes and DIFAT sectors once the FAT passes the 109 header slots. A stream above `MAX_STREAM_SIZE`, 2 GiB (2,147,483,648 bytes, the version 3 limit), is `SIZE_LIMIT`. Tests: `difat_sectors_carry_an_8_mib_stream`, `stream_over_2_gib_is_a_size_limit` and `existing_layouts_open_in_cfb`, which opens the output with the independent `cfb` crate.

## Encryption

The code is in `crates/modern-xlsx-core/src/ole2/crypto/` and `crates/modern-xlsx-core/src/ole2/encryption_info.rs`, on the RustCrypto crates. The `crypto` module (key derivation, password checks, decryption and encryption) is compiled only with the `encryption` Cargo feature, on by default and off in the lite build: `crypto.rs` holds the key derivation, the AES-CBC, hash and HMAC primitives, the package size check, `decrypt_file` and `encrypt_file`; `crypto/agile.rs` the Agile password check, segment cipher, `dataIntegrity` HMAC and writer; `crypto/standard.rs` the Standard (AES-ECB) password check and decryption. The `EncryptionInfo` parser in `encryption_info.rs` uses no crypto crate and is built in every build, so the lite build applies the same descriptor checks.

### Reading

- `EncryptionInfo::parse` validates the descriptor before any key derivation. For Agile (version 4.4), the `keyData` and password `encryptedKey` elements need `keyBits` 128, 192 or 256, `cipherAlgorithm` AES, `cipherChaining` ChainingModeCBC, `blockSize` 16, a known `hashAlgorithm` (SHA-1, SHA-256, SHA-384 or SHA-512) with `hashSize` equal to its digest length, and `saltSize` equal to the decoded salt length (`CipherAttrs::finish`). For Standard (versions 2.2, 3.2 and 4.2), the header must be AES CryptoAPI with SHA-1, `KeySize` must match `AlgID`, and the verifier must have `SaltSize` 16 and `VerifierHashSize` 20. A failure is `PASSWORD_PROTECTED`.
- A `spinCount` above `MAX_SPIN_COUNT` (10,000,000, the MS-OFFCRYPTO maximum), including a decimal too large for 32 bits, is `SECURITY`. `check_kdf_params` repeats the spin-count and key-size checks in `verify_password_agile`, `standard_key` and `encrypt_file_with`, before any hashing, so a descriptor built by hand is held to them too.
- The password check compares in constant time: `constant_time_eq` in `verify_password_agile` and `verify_password_standard`. A wrong password is `PASSWORD_PROTECTED` with the message "Incorrect password." and nothing else.
- For Agile, `verify_hmac` checks the `dataIntegrity` HMAC of the whole `EncryptedPackage` stream before decryption, in constant time (`Mac::verify_slice`). A mismatch is `PASSWORD_PROTECTED`. It also accepts the HMAC layout modern-xlsx 1.2.x wrote; both layouts need the secret key, so neither lets anyone without the password forge a package.
- The `EncryptedPackage` size prefix is attacker-controlled: `declared_package_size` makes a size above the stream's payload `SECURITY`.
- Derived and unlocked keys are `Zeroizing` buffers, wiped on drop on every path. `iterated_hash` keeps the UTF-16LE password in a `Zeroizing` buffer sized up front, so it never reallocates, and wipes the hash chain buffer; `finalize_key` and `standard_key` wipe their intermediate digests.

Tests: `hmac_tamper_case` in `crates/modern-xlsx-core/tests/hostile_inputs.rs` (one flipped byte in the package), with the `spinCount` 4,294,967,295 and `keyBits` `0xFFFFFFF8` cases of `ole2_cases`; `crates/modern-xlsx-core/tests/security_tests.rs`, among them `test_no_key_in_error_messages`, `test_wrong_password_rejected_correct_accepted`, `test_malformed_encryption_info_no_panic`, `test_truncated_encrypted_package_no_panic` and `test_empty_encrypted_package_no_panic`; in `crates/modern-xlsx-core/src/ole2/encryption_info.rs`, `spin_count_above_cap_is_security_error`, `block_salt_and_hash_sizes_are_validated`, `encrypted_key_bits_out_of_range_rejected_at_parse`, `standard_header_flags_alg_and_key_size_are_validated` and `standard_verifier_sizes_are_validated`; in `crates/modern-xlsx-core/src/ole2/crypto/tests.rs`, `verify_hmac_rejects_tampered_package`, `decrypt_package_rejects_declared_size_above_payload` and `derived_keys_are_zeroizing`.

### Writing

The writer always uses Agile encryption with Excel's defaults: `encrypt_file` calls `encrypt_file_with` with SHA-512, a 256-bit AES key and 100,000 spin-count rounds. The two 16-byte salts (`WRITE_SALT_SIZE`), the secret key, the verifier input and the HMAC key come from `secure_random`, which uses `getrandom` (the operating system's generator natively, the browser's Crypto.getRandomValues through its `wasm_js` feature in WASM). Standard encryption is read-only.

Tests: the decryption fixtures in `crates/modern-xlsx-core/tests/interop/main.rs` (msoffcrypto-tool's Agile and Standard fixtures, and modern-xlsx 1.2.1's own output), and `msoffcrypto_oracle_decrypts_our_output`, which has msoffcrypto-tool, an independent implementation, decrypt what this crate writes. That test is ignored in normal runs; the CI job `encryption-oracle` runs it, and publishing needs it to pass.

## Formula engine

The formula engine in `packages/modern-xlsx/src/formula/` runs only when the application calls it, for example through `parseFormula` or `evaluateFormula`; reading a workbook keeps formulas as text and evaluates nothing. Its bounds:

- `parseFormula` in `packages/modern-xlsx/src/formula/parser.ts` refuses a body longer than `MAX_FORMULA_LENGTH` (8192 characters) before tokenizing it. Nesting deeper than `MAX_NESTING_DEPTH` (256) gives 'Formula nested too deeply', and functions nested deeper than `MAX_FUNCTION_DEPTH` (64, Excel's limit) give 'More than 64 nested function levels'; the parser abandons the input instead of recursing further.
- Without `EvalContext.getBounds`, a range of more than `MAX_UNBOUNDED_CELLS` (1,048,576 cells) resolves to `#NUM!` instead of being read (`packages/modern-xlsx/src/formula/resolver.ts` and `packages/modern-xlsx/src/formula/functions/math-stats.ts`). With bounds, a range is clamped to the sheet.
- Wildcard criteria (`COUNTIF`, `SUMIF`, `MATCH` and the rest) use `compileGlob` and `searchGlob` in `packages/modern-xlsx/src/formula/functions/glob.ts`: no regular expressions, and a two-pointer scan that backtracks only to the last `*`, so a hostile pattern costs at most pattern length × text length.
- `REPT` refuses a result longer than `MAX_TEXT_LENGTH` (32,767 characters), and a `RangeError` during evaluation, such as call-stack exhaustion on a very deep tree, becomes `#NUM!` (`stackSafe` in `packages/modern-xlsx/src/formula/evaluator.ts`).

Tests: `packages/modern-xlsx/__tests__/formula-dos.test.ts` ('range bounds', 'parser limits', 'criteria' with 'finishes a ReDoS-shaped criteria quickly', 'REPT cap') and `packages/modern-xlsx/__tests__/formula-glob.test.ts`.

## CSV export

`sheetToCsv` in `packages/modern-xlsx/src/io/sheet-utils.ts` writes cell text as it is. Its `escapeFormulas` option defuses CSV injection: a value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a `'` prefix and is quoted, except a `number` cell that holds a plain decimal literal such as `-5`. The option is off by default (`escapeFormulas` is `false` unless set), so an application that exports untrusted workbooks to CSV for a spreadsheet program must turn it on.

Tests: `packages/modern-xlsx/__tests__/sheet-utils.test.ts` ('sheetToCsv quoting and formula escaping', 'sheetToCsv formula escaping does not trust the declared cellType').

## Language and build

- The workspace forbids unsafe Rust: `unsafe_code = "forbid"` under `[workspace.lints.rust]` in the root `Cargo.toml`. The hostile-input suite keeps it in force by counting allocations through `peak_alloc`, a safe API.
- The release profile sets `panic = "abort"`. A panic in WASM is a trap, which JavaScript sees as `WASM_ERROR`; `packages/modern-xlsx/__tests__/hostile-input.test.ts` asserts the coded error for each hostile case, never `WASM_ERROR`.
- Six fuzz targets in `fuzz/fuzz_targets/` cover the read paths (`read_xlsx`, `read_xlsx_json`, `read_xlsx_json_with_password`), the write path read back (`write_xlsx_json`), validation and repair (`validate_repair`) and the streaming writer (`streaming_writer`). The CI job `fuzz` runs each for 30 seconds with the seeds in `fuzz/seeds/`. It is not among the jobs publishing needs.

## Known limitations

- **Standard encryption is legacy cryptography.** Standard (read only) derives its key with SHA-1 and a fixed 50,000 rounds (`STANDARD_SPIN_COUNT`), and decrypts both the verifier and the package with AES-ECB, as MS-OFFCRYPTO specifies. It has no integrity check: `decrypt_file` runs `verify_hmac` for Agile only, so nothing checks a Standard package before the ZIP reader sees the decrypted bytes. The writer never produces Standard encryption.
- **Not every intermediate is wiped.** `verify_password_standard` keeps the decrypted verifier, its SHA-1 hash and the decrypted verifier hash in plain `Vec` buffers, as `verify_password_agile` does for the hash it computes from the verifier input, and `encrypt_file_with` for the verifier input and its hash. The hash and HMAC states inside the RustCrypto crates are not wiped either: the workspace does not enable the `zeroize` feature of `digest`, `sha1` or `sha2`. The decrypted package is plain memory, and the password arrives as a JavaScript string, which no code can wipe.
- **Base64 is hand-written.** `encode_base64` and `decode_base64`, both in `crates/modern-xlsx-core/src/ole2/base64.rs`, replace a dependency. The decoder is lenient: it skips `=`, spaces, CR and LF anywhere and drops trailing bits short of a byte. A decoding fault makes decryption fail; it does not expose a secret.
- **Key derivation cost.** A file may declare up to 10,000,000 spin-count rounds, 100 times Excel's default, and reading it with a password runs all of them. The key derivation runs only when a password is given. A `spinCount` of 0 parses, as MS-OFFCRYPTO allows (`spin_count_at_cap_and_zero_parse`); it weakens only that file.
- **The limits bound bytes, not memory.** `read_zip_entries` holds every entry decompressed at once before the parts are parsed, and the parsed model and the JSON come on top. The memory of defined names, shared strings, style records, chart series and axes, threaded comments and worksheet lists is counted (see Output size), but the rows and cells of the model path are not, and tables, pivot parts, persons, slicers, timelines, drawing anchors and comments are bounded only by their part size times their parser's factor. A read inside the 2 GiB default can therefore need more memory than a 32-bit WASM instance has. For untrusted input, lower `maxDecompressedSize`.
- **Shared text is counted when it is copied.** A comments part that later turns out malformed, or the cells of a last row cut off by the end of its worksheet part, count toward `max_json_length` while their part is read, though they never reach the result: such a part fails the read with `SIZE_LIMIT` when its copies alone pass the limit, instead of being dropped. With the `parallel` Cargo feature (not in the WASM build) each sheet counts from the count before the sheets, so the limit holds per sheet while sheets parse, and across sheets once all are parsed. The count of worksheet list memory is per sheet under that feature, each sheet's lists together with the records counted before the sheets (defined names, shared strings, style records, chart series and axes, threaded comments), so the sheets of one read can together keep up to their number times the limit.
- **The WebAssembly memory grows in small steps.** Through the WebAssembly build, a read that builds hundreds of MB of output from small allocations pays for each growth of the memory in proportion to the memory already held, so its time grows faster than its output; the native Rust crate reads the shared-string shape below in linear time. Rich shared strings: 2,800,000 one-run entries (`<si><r></r></si>`, a 475,417-byte package) read in about 3.5 s at 797 MiB of WebAssembly memory, where a read with the memory grown first took 0.66 s (measured on 2026-11-13); the shared-string charge refuses the 2,917,776th entry, which bounds the time. Kept worksheet extensions: a 1,965,765-byte package whose root declares 1,000 prefixes used by each of 11,500 kept `<ext>` reads 343 MB of JSON in about 3.7 s (3,715 and 3,726 ms, two runs; 3,704 and 3,746 ms with the declarations on `<extLst>`), where the same JSON from `<ext>` elements that declare the prefixes themselves, so nothing is inserted, takes 3.0 s (2,980 and 2,994 ms) and the native JSON read of the first package 2.0 s; in an instance whose memory had already grown by 1.5 GiB the first package took 10.9 to 15.1 s, the `<extLst>` form 15.1 to 17.0 s and the control 3.0 to 3.2 s, where the same runs without that growth took 4.1 to 4.5 s, 5.9 to 6.3 s and 3.1 s on a host shared with other work. The other extension figures were measured on 2026-11-14 on an otherwise idle host, with the release WebAssembly module under Node v26.13.0 and the native release profile; the JSON length check bounds them, since every inserted declaration is counted against `maxJsonLength`. Growing the memory in larger steps is planned for 1.4.0.
- **The worker takes no limits.** `readBuffer` of `createXlsxWorker` takes only a password, so worker reads use the default limits.
- **Rust callers are trusted.** `read_xlsx_with_options` and the other Rust entry points use the `ZipSecurityLimits` they are given as is; only the WASM bridge clamps. A Rust application that takes limits from outside calls `ZipSecurityLimits::clamped` first.
- **`validate()` scans the pivot caches.** `validate_pivot_additions` in `crates/modern-xlsx-core/src/validate.rs` looks up each pivot table's cache by scanning every cache, so its cost is pivot tables times caches; the writer looks a cache up by id in one step. `maxEntries` bounds both counts, and 49,000 tables over 49,000 caches validated in about half a second.
- **`readBuffer` does not check its argument's type.** Passing `null` gives `WASM_ERROR` ('null gives WASM_ERROR' in `packages/modern-xlsx/__tests__/hostile-input.test.ts`), not a coded rejection.
