# Changelog

All notable changes to this project are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/), and this project adheres to [Semantic Versioning](https://semver.org/).

Versions 0.1.0, 0.1.9, 0.2.0, 0.3.0, 0.4.0, 0.6.0, 0.9.0, 0.9.1 and 0.9.2 exist as git tags only and were never published to npm. Version 1.0.0-rc.1 was published to npm under the `next` dist-tag and has no section of its own here. Version 0.1.9 has no section either.

## [Unreleased]

1.3.0 makes the workbooks modern-xlsx writes open in Excel as written, bounds what a hostile file can cost the reader, and makes the formula engine compute what Excel computes; some output and some error codes change on purpose, so read **Upgrading from 1.2.x** before you update.

### Highlights

- **Files Excel opens as written.** Every written workbook has a theme, colours are written as ARGB, sheet protection follows the ECMA-376 defaults, comments get the VML note drawing Excel draws them from, threaded comments get the GUID ids Excel requires, and table totals rows, pivot tables and custom row heights are written in the form Excel reads.
- **Values Excel refuses fail the write.** A colour that is not 6 or 8 hex digits, a `password` that is not the legacy hash, a chart whose series share an `order` and two pivot caches with one `cacheId` fail the write with `INVALID_WORKBOOK` naming where they sit, instead of reaching the file; `validate()` reports the colour, password and chart cases as errors.
- **Safe on hostile files.** ZIP bombs, forged ZIP sizes, malformed OLE2 containers, encryption headers with an oversized `spinCount` or stream size, and files built to amplify (one shared string named by many cells, millions of empty records) fail with `SECURITY` or `SIZE_LIMIT` instead of exhausting memory or trapping the WebAssembly module; the shapes that can still trap it or reach its memory ceiling are a workbook field of control characters, listed under Known limitations in the full changelog, and uncharged pivot cache fields, which the threat model describes. `ReadOptions.limits` sets the limits per read, and the [threat model](https://github.com/ABCrimson/modern-xlsx/blob/v1.3.0/docs/security/threat-model.md) describes each defence.
- **Nothing lost on read.** A malformed optional part (comments, tables, charts and their drawings, pivot tables, threaded comments, slicers, timelines and others) no longer fails the read: it is kept verbatim in `preservedEntries` and survives a write.
- **Excel's formula semantics.** `^` associativity, text-to-number coercion, blank-cell comparison, criteria matching, rounding, lookups and `TEXT` give Excel's results, and the parser reads whole-column, structured and 3-D references.
- **Encryption.** Password-protected workbooks saved by Excel (Agile, AES-256 with SHA-512) open; 1.2.1 failed on them with "AES decryption failed (bad padding)". AES-192 encrypted workbooks (Agile `keyBits` 192 and Standard AES-192) and Agile files whose `dataIntegrity` HMAC uses SHA-1 or SHA-384 decrypt too. Workbooks are encrypted with Agile AES-256 and SHA-512 at 100,000 spins, as Excel encrypts them.
- **New in the API.** `SheetProtectionData.plainPassword` protects a sheet with a password hashed as Excel hashes it; `ReadOptions.limits`; the `modern-xlsx/wasm` subpath, a compiled module for `initWasmSync()` on Cloudflare Workers; `using` with `XlsxWorker` and `StreamingXlsxWriter`; `TemporalLike` for native `Temporal` dates; and round-trip fields such as `colorSpec` for theme colours, `RowData.customHeight` and the remaining conditional-format and data-validation attributes.
- **Errors and builds.** New error codes `SIZE_LIMIT`, `JSON`, `INVALID_WORKBOOK` and `WORKER_ERROR`; release WebAssembly builds run `wasm-opt -Oz` and hold no paths of the build machine; the npm package is the tarball CI packed and tested.

### Upgrading from 1.2.x

- **Default font:** new workbooks, and `font()` without a name, use Calibri, not Aptos. Pass `name: 'Aptos'` to `font()` to keep Aptos.
- **Colours:** a colour that is not 6 or 8 hex digits after an optional `#` (such as `'red'`) fails the write with `INVALID_WORKBOOK`: pass hex. Colours are written and read back as uppercase ARGB (`'#ff0000'` reads back as `'FFFF0000'`): compare against that form.
- **Sheet protection:** a flag set to `false` is now written and allows that action in Excel, and an absent flag reads as `true` (locked): set a flag to `true` to keep its action locked. `password` takes only the 1 to 4 hex digit legacy hash: put a plain password in the new `plainPassword`.
- **Hyperlinks:** external URLs are read into `HyperlinkData.target`, no longer into `location`: read the URL from `target`.
- **Error codes:** malformed workbook JSON fails with `JSON` (was `WASM_ERROR`), a workbook without sheets fails with `INVALID_WORKBOOK` (was `INVALID_CELL_VALUE`), and a malformed attribute in a worksheet or a malformed numeric attribute in `xl/styles.xml` fails the read with `XML_PARSE` instead of being read as a default: update code that matches on `error.code`.
- **Threaded comments:** ids are upper-case GUIDs in braces, and a cell holds one thread: `addThreadedComment` on a cell that has one throws `INVALID_ARGUMENT`, so add to it with `replyToComment`.
- **Pivot tables:** `pivotCaches` lists the caches that have records first: find a pivot table's cache by its `cacheId`, not by its position.
- **Formulas:** results follow Excel, for example `2^3^2` is 64, `ROUND(-2.5,0)` is -3 and `SUM(1;2)` is `#VALUE!`: recheck the expected values your tests pin.
- **Cell values:** setting a cell to `NaN` or an infinite number, directly or through `aoaToSheet` or `jsonToSheet`, throws `INVALID_CELL_VALUE` (1.2.1 stored `NaN`): filter such values before you write them.
- **Sheet names:** `addSheet`, `renameSheet`, the `Worksheet.name` setter and `cloneSheet` throw `INVALID_ARGUMENT` for a name equal to another sheet's ignoring case and canonical equivalence (`DATA` beside `data`), which Excel refuses to open, for `History`, which Excel reserves, and for a name with a control character.
- **Charts:** `ChartBuilder.addSeries({ lineWidth })` takes points, not EMU: pass 2 for a 2-point line (written only with `lineColor`).
- **Reading:** a `t="d"` cell reads as the date serial number, not its ISO text, and `sheetToJson` with `range` includes the range's last row.
- **Rust crate:** the error enum's `help()` and `docs_url()` methods and its `InvalidStyle`, `InvalidFormat` and `Io` variants are removed: use `code()`, which is unchanged.
- **CSV, text and HTML:** `sheetToCsv`, `sheetToTxt` and `sheetToHtml` write a boolean cell as `TRUE` or `FALSE`, not `1` or `0`: update code that parses their output.

The full list in `CHANGELOG.md` gives every change, the 150 behaviour changes included, and the conditions of its measured figures under **Measurement notes**.

### Security

- **Reading:** a ZIP bomb or an archive with a forged size no longer inflates in full or traps the WebAssembly module: each entry inflates only up to what is left of the total budget and its compression-ratio cap, then the read fails with `SECURITY`.
- **Reading:** an archive with duplicate entry names, more ZIP entries than `maxEntries` (default 100,000), or an entry name that contains a NUL byte or starts with a drive prefix such as `C:` is rejected with `SECURITY`.
- **Reading:** an archive in which an entry's declared data overlaps another entry or the central directory is rejected with `SECURITY`, so a forged compressed size cannot raise the entry's compression-ratio cap.
- **Reading:** a workbook whose preserved parts would push the read JSON past `ReadOptions.limits.maxJsonLength` is rejected with `SIZE_LIMIT` before that JSON is built, so a large media part no longer runs the WebAssembly module out of memory.
- **Reading:** a read fails fast with `SIZE_LIMIT` when text stored once in the file is copied past `ReadOptions.limits.maxJsonLength` (default 536,870,888 bytes): one shared string named by many cells, one comment author on many comments, or one hyperlink target named by many hyperlinks. Before, a 77 KB file (one 100,000-character shared string in 10,000 cells) built a 964 MiB model and failed only once the JSON reached 1.0 GB (peak 1.7 GiB), a 68 KB file (one 100,000-character author on 10,000 notes) peaked at 3.8 GiB, and with 30,000 cells the WASM build trapped (`RuntimeError: unreachable`) after 1.1 s at 2.4 GiB, with 30,000 notes after 311 s. Each now fails in about 0.25-0.5 s natively. The JSON a read returns is also checked after each shared string a cell's `<v>` names and each cell, comment, hyperlink, kept extension and workbook field, since text copied this way is written escaped (a control character takes 6 bytes of JSON): one 40,000-control-character shared string named by the 16,384 cells of one row (an 84 KB file) wrote about 3.2 GB of JSON (native peak 7.4 GiB) before it failed, and trapped the WASM build (`RuntimeError: unreachable`); it now fails with `SIZE_LIMIT` in about 0.5 s natively at a peak of about 0.8 GiB. One cell with 13,000 `<v>` naming one 40,000-control-character string (a 53 KB file) wrote 3.1 GB natively and trapped the WASM build; it now fails with `SIZE_LIMIT` in about 0.4 s at a 0.9 GiB peak. The same holds for a namespace the worksheet root declares once and every kept worksheet extension (`<extLst><ext>`) re-declares: a 33 KB file with one 100,000-character namespace on 5,000 extensions read to 500 MB at a 1.9 GiB peak, and with 6,000 peaked at 2.3 GiB; it now fails with `SIZE_LIMIT` at about 0.5 GiB. 1.2.1 had the shared-string and author expansion (with no JSON limit at all); the hyperlink one came with this release's external hyperlinks, and the extension one with its self-contained kept extensions. The Rust crate's `read_xlsx` and its variants (not part of the npm package) count a cell's shared string once when the cell has several `<v>` elements. No workbook that read before is refused for the text it copies: the JSON of a read holds every such copy, so a read past the limit could not have returned its JSON (see Known limitations for a truncated or malformed part; the memory of the defined names, shared strings, style records, chart series and axes, threaded comments and worksheet lists a read keeps is counted against the same limit, see Behaviour changes).
- **Reading:** the JSON length limit is checked after every worksheet row, not only after each sheet, so a large sheet stops as soon as the JSON passes the limit.
- **Reading:** reading a worksheet counts the memory of every element it keeps in a list (data validations, conditional formats and their rules, selections, columns, hyperlinks, merged ranges, page breaks, filters, sparklines, kept extensions) against `ReadOptions.limits.maxJsonLength` (`ZipSecurityLimits::max_json_length` in the Rust crate), at the size of its record plus its strings, so a part of millions of tiny elements fails with `SIZE_LIMIT` instead of exhausting memory (see Behaviour changes). 1.2.1 had this class: 9,000,000 `<cfRule/>` in a 1.4 MB file took 3,943 MiB of WebAssembly memory, near the 4 GiB trap, and read. The charge is each element's size in memory, so the WebAssembly build keeps 1.5 to 1.9 times as many elements as the 64-bit Rust crate before `SIZE_LIMIT`; that file now ends in `SIZE_LIMIT` in both, in 0.3 s natively and at 2,055 MiB of WebAssembly memory (measured on 2026-11-13, a UTC date).
- **Reading:** a styles part (`xl/styles.xml`) of millions of empty records (`<dxf/>`, `<border/>`, `<fill/>`, `<font/>`, `<xf/>`, gradient `<stop/>`) no longer exhausts memory: each style record is counted, at its size in memory, against the same limit as the worksheet lists (`ReadOptions.limits.maxJsonLength` / `ZipSecurityLimits.max_json_length`), and the read fails with `SIZE_LIMIT` (see Behaviour changes). A 295 KB package of 3,300,000 `<dxf/>` now fails at 1,590 MiB of WebAssembly memory (919 MiB natively); without the count it trapped the WebAssembly build (`RuntimeError: unreachable` at 3,158 MiB) and took 7,219 MiB (7.0 GiB) natively. 1.2.1 read that file in 25 MiB: the trap came with this release's larger style records. These figures were measured on 2026-11-13.
- **Reading:** a worksheet of millions of page breaks (15,000,000 in a 9.4 MB file) no longer makes `readBuffer` and the other JSON reads build one string of about 570 MB before its length is checked: page breaks, the auto filter's columns, values and custom filters, and tables are written one element at a time, and the read fails with `SIZE_LIMIT` as soon as the JSON passes `ReadOptions.limits.maxJsonLength`. 1.2.1 failed to read such a file with a JavaScript `ERR_STRING_TOO_LONG` error. Measured on 2026-11-13.
- **Reading:** a shared strings part of millions of empty rich text runs no longer exhausts memory: each entry and run is counted against the same limit and the read fails with `SIZE_LIMIT` (see Behaviour changes). One entry of 10,000,000 empty `<r></r>` runs (an 820,932-byte package) now fails in 535 ms through the WebAssembly build and natively in 0.5 s at a 1,618 MiB peak; without the count it trapped the WebAssembly build (`RuntimeError: unreachable` at 2,675 MiB) and took 6,080 MiB natively. 1.2.1 read that file at 1,863 MiB and trapped at 40,000,000 runs: the trap at the smaller count came with this release's larger rich text run record. These figures were measured on 2026-11-13.
- **Charts, threaded comments and defined names:** a chart of millions of empty series or axes, a threaded comments part of millions of empty comments and a workbook part of millions of defined names no longer trap the WebAssembly build: each record is counted against the same limit, and the read fails with `SIZE_LIMIT` in 0.7 to 1.1 s (see Behaviour changes). Without the count, 135 MB of empty `<ser><tx/></ser>` series in a chart (a 1,362,906-byte package), 128 MB of empty `<catAx></catAx>` in a chart (1,292,798 bytes), 183 MB of `<threadedComment/>` (1,846,713 bytes) or 196 MB of `<definedName name="a"/>` (1,977,509 bytes) trapped the WebAssembly build (`RuntimeError: unreachable` at 2,187 to 2,923 MiB). 1.2.1 read each of these files: it kept no axis beyond the modelled ones, no threaded comment without attributes and no self-closing defined name, and its read of such `<ser><tx/></ser>` series traps from 137 MB (of empty `<ser></ser>` from 94 MB, where 1.3.0 now fails with `SIZE_LIMIT`). These figures were measured on 2026-11-13.
- **Reading:** a part is parsed at most once per read, however many relationships, sheets, drawings or pivot cache definitions name it. A crafted package that pointed thousands of relationships at one comments, threaded-comments, slicer, timeline, table, drawing, chart, pivot table, pivot cache or slicer or timeline cache part multiplied that part's parsed output and parse time; the repeats are skipped and logged as one summary warning per kind of part. A workbook with thousands of `<sheet>` entries on one worksheet part, which 1.2.1 parsed once per entry, now fails the read with `SECURITY` (see Behaviour changes).
- **Tables and comments:** a crafted package of thread roots or legacy notes on distinct cells no longer makes read-then-write run for seconds and allocate gigabytes. The writer generates a VML note shape (about 640 bytes) for each legacy comment without one and a `tc=` placeholder note (about 430 bytes) for each thread root without a legacy comment, so a 6 MB file of 2,000,000 thread roots wrote for 10.6 s with a 3.66 GiB peak heap and trapped the WASM build (`WASM_ERROR`). One write now generates at most 131,072 such notes and fails with `SIZE_LIMIT` past it, before the oversized parts are built (1,000,000 roots fail within 1 s and 16 MiB of peak heap). Notes kept in the note drawing a workbook was read with are not counted, so a file Excel saved is written back whatever its number of notes. 1.2.1 generated no note drawing and no placeholders.
- **Reading:** a part whose root declares many namespace prefixes no longer makes hyperlink parsing, or each element the reader keeps verbatim (a styles `<colors>`, `<tableStyles>` or `<extLst>`, a worksheet `<ext>`, a pivot `<cacheSource>`), take time proportional to the number of declarations: a kept element now costs its own length plus, per prefix it uses or declares, a search logarithmic in the declarations, and no lookup on that path goes through a hasher whose keys a file could make collide (through the WebAssembly build a read that inserts hundreds of MB of declarations also pays for the growth of the memory, see Known limitations). A 198,621-byte package with 50,000 declarations on the styles root and 20,000 `<colors/>` took 35.0 s natively and 17.9 s through the WebAssembly build, and the same declarations with 20,000 worksheet `<ext uri="a"/>` 37.8 s natively; they now read in 13 ms and 15 ms natively and in 58 ms each through the WebAssembly build. A kept worksheet `<ext>` copies each namespace declaration it inherits from the `<worksheet>` root from text rendered once per sheet, found by a binary search of the root's declarations: a 1,965,760-byte package whose root declares 1,000 prefixes used by each of 11,500 `<ext>` (11,500,000 inherited declarations) reads in 3.90 to 4.35 s through the release WebAssembly build, where an earlier 1.3.0 development build, which formatted, escaped and allocated each declaration, took 5.24 to 5.45 s, and the same `<ext>` elements declaring their prefixes themselves take 3.43 to 3.52 s; natively the model read takes 1.91 s and the JSON read 2.26 s (3.42 s and 3.72 s in that build), and 1.2.1, which keeps no worksheet `<ext>`, reads the file in 0.16 s. A verbatim element repeated under one long namespace URI no longer copies the URI once per repeat: a 306 KB package with a 400,000-byte URI and 50,000 repeats took 29 s natively and in WebAssembly, and its styles and pivot forms now read in 0.12 s and 0.42 s even in an unoptimized build. The last occurrence of a repeated element is kept, as before. 1.2.1 did not have these costs: it kept no `<colors>`, `<tableStyles>` or `<extLst>` of the styles part and no `<cacheSource>` verbatim, and re-declared no namespaces on `<ext>`. These figures were measured on 2026-11-13.
- **Charts:** a crafted chart part with many `c:axId` entries and many axes no longer takes quadratic time to read: at most three axis ids per chart type are read, as the schema allows.
- **Reading:** a malformed OLE2 (MS-CFB) container can no longer panic, trap the WebAssembly module or force a huge allocation through a looping sector chain, a FAT sector listed twice or a stream length larger than its chain. These fail with `SECURITY`, and an invalid header fails with `UNRECOGNIZED_FORMAT`.
- **Encryption:** an Agile `EncryptionInfo` whose `spinCount` is above 10,000,000, the MS-OFFCRYPTO maximum, is rejected with `SECURITY` instead of keeping the reader busy; a missing or non-numeric `spinCount` is a `PASSWORD_PROTECTED` "malformed EncryptionInfo" error instead of 0.
- **Encryption:** an `EncryptedPackage` stream whose size field declares more bytes than the stream holds is rejected with `SECURITY` instead of crashing, running out of memory or returning a truncated package.
- **Encryption:** a Standard `EncryptionInfo` with a hostile `headerSize` no longer traps the WebAssembly module; it is reported as `PASSWORD_PROTECTED`.
- **Encryption:** an `EncryptionInfo` whose hash size does not match its hash algorithm, a hash size of 0 included, is rejected with `PASSWORD_PROTECTED`. 1.2.1 let a hash size of 0 pass the password and integrity checks without comparing any bytes.
- **Encryption:** a key size other than 128, 192 or 256 bits is rejected as unsupported encryption (`PASSWORD_PROTECTED`) before any key derivation runs, and derived key material is wiped from memory when it is dropped.
- **Worksheets:** a frozen pane or cell reference past `XFD1048576` no longer traps the WebAssembly module; a frozen pane past the sheet edge fails the write with `INVALID_CELL_REF`.
- **Worksheets:** `validate()` on a very large merge range such as `A1:XFD1048576` returns at once instead of running for a time proportional to the range's area.
- **Workbook and worksheet API:** `validate()` and `repair()` no longer amplify a small file into gigabytes of report text or trap the WASM build, because the report they return is bounded (see Behaviour changes): a 180 KB file with a 100,000-character table name and 16,384 totals cells gave 1.64 GB of text (peak 3.1 GiB, a WASM trap after 117 s), a 78 KB file with a 100,000-character sheet name gave 1.0 GB, and a file of 2,000,000 thread roots gave 4,000,000 issues (719 MB, a WASM trap after 195 s). 1.2.1 had the unbounded report and the sheet-name amplification; the table-name, totals and thread checks are new in this release.
- **Tables and comments:** the table totals-row check of `validate()` (new in this release) runs in time linear in the sheet's rows and the tables' columns: 10,000 tables over a sheet's last row took 31 s and 100 tables of 16,384 columns 18 s natively (28 s in WASM); they now take 89 ms and 186 ms natively (the second 0.35 s in WASM). The `@` shorthand check of `validate()` and `addTable` (new in this release) runs in time linear in the formulas' length and the tables' columns: four tables of 16,384 columns with `[@x]` in every column took 38.9 s natively and 18.5 s in WASM, and now take 15 ms natively and 29 ms in WASM; `addTable` of one 16,384-column table with `[@x]` in every column took 3 s and now takes 7 ms.
- **Workbook parts:** reading a workbook with a very large calculation chain and many sheets takes time linear in their sizes instead of quadratic, and the pivot cache lookup is linear too.
- **Reading (Rust crate):** the reader's `log` output names missing, malformed and unparsed parts in one summary line per kind (the count and the first example) instead of one line per relationship or ZIP entry, and every piece of file text it logs is escaped (a newline prints as `\n`, ESC as `\u{1b}`) and cut at 160 bytes. A crafted package can no longer flood a host's log or write newlines and terminal control sequences into it.
- **Streaming writer:** a number value can no longer inject XML into the sheet.
- **Build and dependencies:** zip 8.6.0 is replaced by 9.5.1, which is outside the affected ranges of [RUSTSEC-2026-0367](https://rustsec.org/advisories/RUSTSEC-2026-0367.html), [RUSTSEC-2026-0368](https://rustsec.org/advisories/RUSTSEC-2026-0368.html) and [RUSTSEC-2026-0369](https://rustsec.org/advisories/RUSTSEC-2026-0369.html) (patched in zip 9.0.0). All three concern zip's archive extraction to disk, which modern-xlsx does not call.
- **Build and dependencies:** ctutils 0.4.2, a dependency of the `digest` crate under the hash and HMAC crates, is replaced by 0.4.8, which is outside the affected range of [RUSTSEC-2026-0385](https://rustsec.org/advisories/RUSTSEC-2026-0385.html) (non-constant-time mask generation and `u128` comparisons, patched in 0.4.4).
- **Utilities and CLI:** `sheetToCsv` and `sheetToTxt` take `escapeFormulas: true` to defuse CSV injection: a value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a `'` prefix and is quoted, whatever the cell's type, so `=1+2` is written as `"'=1+2"`. Only a number cell holding a finite decimal literal, such as `-5`, is left as it is.
- **Utilities and CLI:** `sheetToCsv`, `sheetToTxt` and `sheetToHtml` throw `ModernXlsxError` `SIZE_LIMIT` when the output grid (the rows from the first to the last populated row, times the columns up to the widest row) could not fit in one JavaScript string, instead of running until the process is out of memory, as a sheet holding only A1 and XFD1048576 did.
- **Formula engine:** COUNTIF, SUMIF and AVERAGEIF wildcard criteria and SEARCH match without regular expressions, so a hostile pattern cannot trigger catastrophic backtracking. 1.2.1 compiled each wildcard criterion into a `RegExp`, so a crafted pattern could stall evaluation.
- **Formula engine:** `evaluateFormula` and `evaluateNode` return `#NUM!` instead of throwing a stack-overflow `RangeError`, and `parseFormula` stops at its nesting limits instead of overflowing the stack.
- **Formula engine:** text results are held to Excel's 32,767 characters, so a hostile formula can no longer build a string of hundreds of millions of characters through `&`, CONCATENATE or SUBSTITUTE, and TRIM runs in linear time on text with long runs of spaces.
- **Number formats and dates:** `formatCell` and `formatCellRich` run in linear time on a numeric-looking string value or a format condition with a long digit run, and on long comma runs and month runs, and a date format code of a million tokens no longer throws `RangeError`.
- **Barcodes:** `encodeQR` rejects input longer than 652 characters, the most a version 1-10 symbol holds, before it encodes anything.

### Added

- **Reading:** `ReadOptions.limits` sets the read limits for `readBuffer` and `readFile`: `maxDecompressedSize` (default and ceiling 2,147,483,648 bytes), `maxCompressionRatio` (default 100, no ceiling), `maxEntries` (default 100,000, ceiling 1,048,576) and `maxJsonLength` (default and ceiling 536,870,888 bytes), which also bounds the text a read copies from shared strings, comment authors, hyperlink targets and the worksheet namespace declarations it copies onto kept extensions, and the memory of the records a read keeps for its defined names, shared strings, styles, chart series and axes, threaded comments and worksheet lists (see Behaviour changes). A value above its ceiling is clamped. An unknown key, or a value that is not a finite number greater than zero (a safe integer for the byte and entry counts), throws `INVALID_ARGUMENT`.
- **Reading:** a workbook whose JSON would be longer than `maxJsonLength` rejects with `SIZE_LIMIT` (#31).
- **Errors:** new error codes `SIZE_LIMIT` (a hard size limit: the read JSON length, the shared text a read copies and the memory of the defined names, shared strings, style records, chart series and axes, threaded comments and worksheet lists it keeps, an encrypted write whose OLE2 stream would pass 2 GiB, the pivot items the writer adds to tables built in code, the notes one write generates, or a `sheetToCsv`, `sheetToTxt` or `sheetToHtml` grid too large for one string; the numbers are in the `SIZE_LIMIT` documentation), `JSON` (constant `JSON_ERROR`), `INVALID_WORKBOOK` and `WORKER_ERROR` (a Web Worker transport failure: the worker crashed or was terminated, a message could not be deserialised, or a reply carried no data), exported from `modern-xlsx` and `modern-xlsx/lite`.
- **Encryption:** AES-192 encrypted workbooks (Agile `keyBits` 192 and Standard AES-192) decrypt.
- **Encryption:** Agile files whose `dataIntegrity` HMAC uses SHA-1 or SHA-384 decrypt and verify.
- **Worksheets:** `SheetProtectionData.plainPassword` (write-only) protects a sheet with a password, hashed as Excel does with SHA-512, a random 16-byte salt and 100,000 spins; `modern-xlsx/lite` writes the legacy 16-bit hash instead and accepts ASCII passwords only. `password` holds the legacy hash as stored in the file, not a password.
- **Worksheets:** `SheetProtectionData` gains `insertHyperlinks`, `pivotTables`, `selectLockedCells`, `selectUnlockedCells`, `algorithmName`, `hashValue`, `saltValue` and `spinCount`, so a sheet protected by Excel keeps its password hash through a read and write.
- **Worksheets:** `CellData.cellMetadata` reads and writes the `cm` attribute of dynamic-array formulas, and the writer adds `xl/metadata.xml` with its relationship and content type.
- **Worksheets:** `CellData.formulaDtr`, `formulaDel1` and `formulaDel2` read and write the ECMA-376 data-table attributes `dtr`, `del1` and `del2`.
- **Worksheets:** worksheet `<extLst>` extensions other than sparklines (such as x14 conditional formatting and data validation) are kept in `preservedExtensions` and written back; each kept `<ext>` declares the namespace prefixes it uses that the `<worksheet>` root or its `<extLst>` declares (an `<extLst>` binding wins over the root's), so the written sheet binds every prefix.
- **Worksheets:** theme, indexed, tint and auto colours of data bars, colour scales and tab colours are kept in the new `colorSpec`, `colorSpecs` and `tabColorSpec` fields.
- **Worksheets:** `ColumnInfo` gains `styleIndex` (the `<col style>` format Excel applies to the column), `bestFit` and `phonetic`, read from and written to `<col>`.
- **Worksheets:** `RowData.styleIndex` keeps a row's format (`<row s customFormat="1">`) through a read and write.
- **Worksheets:** `RowData.customHeight` reads and writes the `customHeight` attribute of `<row>`, which tells Excel the row height was set by hand; `setRowHeight` sets it.
- **Pivot tables:** `validate()` warns (category `structure`) about a pivot table whose `cacheId` names no pivot cache, a workbook whose write fails with `INVALID_WORKBOOK`.
- **Worksheets:** `ConditionalFormattingRuleData.additionalFormulas` holds a rule's second and third formulas, so a `cellIs` `between` or `notBetween` rule keeps both bounds; `formula` is still the first. A rule with more than three formulas fails the write with `INVALID_WORKBOOK` naming the sheet, and `validate()` reports it.
- **Worksheets:** `ConditionalFormattingRuleData` gains `stopIfTrue`, `aboveAverage`, `percent`, `bottom`, `text`, `timePeriod`, `rank`, `stdDev` and `equalAverage`, read and written, so a "below average", "bottom N", "contains text" or "dates occurring" rule keeps its meaning through a round trip.
- **Worksheets:** `DataValidationData` gains `errorStyle`, `showDropDown` and `imeMode`, so a warning or information validation no longer becomes a stop validation and a hidden list arrow stays hidden through a round trip.
- **Worksheets:** `SparklineGroupData` gains `minAxisType`, `maxAxisType`, `dateAxis`, `displayHidden`, `dateRange` and a `color*Spec` field beside each colour (theme, indexed, tint and auto colours). A `manualMin` or `manualMax` without an axis type is written with `minAxisType` or `maxAxisType` set to `"custom"`, so Excel applies it.
- **Worksheets:** `PageSetupData.fitToPage` reads and writes `<sheetPr><pageSetUpPr fitToPage>`, so Excel's "Fit to N pages wide by M tall" survives a round trip and applies when written: Excel honours `fitToWidth` and `fitToHeight` only when it is true.
- **Styles:** theme, indexed, tint and auto colours survive a round trip through the new `colorSpec` (fonts, border sides, gradient stops) and `fgColorSpec`/`bgColorSpec` (fills) fields beside the existing `rgb` strings. On write a spec is used while its `rgb` equals the string field; changing the string overrides it.
- **Styles:** `Font.underlineStyle` keeps `'double'`, `'singleAccounting'` and `'doubleAccounting'` underlines; `underline` stays a boolean.
- **Styles:** `cellStyleXfs`, the `xfId` of each cell format, the alignment `readingOrder`, `justifyLastLine` and `relativeIndent`, and differential-format alignment and protection are read and written; `tableStyles`, `colors` and the styles `extLst` are kept verbatim (`tableStylesXml`, `colorsXml`, `extLstXml`).
- **Styles:** `FontData.explicitOff` lists the font flags a differential format writes explicitly off (`<b val="0"/>`, `<u val="none"/>` and the like), so a conditional format's "Regular" or "no underline" override survives a round trip instead of becoming "inherit".
- **Styles:** `CellXfData.quotePrefix` (cells typed with a leading apostrophe, such as `'00123`) and `CellXfData.pivotButton` are read and written; 1.2.1 dropped them.
- **Workbook parts:** new optional workbook fields `calcPr`, `fileVersion`, `workbookPr` and `externalReferences`; defined-name attributes `comment`, `customMenu`, `description`, `help`, `statusBar`, `hidden`, `function`, `vbProcedure`, `xlm`, `functionGroupId`, `shortcutKey`, `publishToServer` and `workbookParameter`; document properties `lastPrinted`, `language`, `identifier`, `version`, `totalTime` and `docSecurity`; and the `calcChain` flags `s`, `l`, `t` and `a`.
- **Pivot tables:** `CacheSource.name` holds the table or defined name a cache is built from (`<worksheetSource name>`), and `CacheSource.rawXml` the whole `<cacheSource>` of a source that is not a worksheet (consolidation, external, scenario), kept opaque and written as read; both are absent when unset.
- **Pivot tables:** `CacheSource.rId` holds the `r:id` of `<worksheetSource>`, and `PivotCacheDefinitionData.relationships` the cache definition's relationships other than the one to its records (`id`, `type`, `target`, `targetMode`), so a source in another workbook keeps its link; both are absent when unset. The writer drops an `r:id`, in `<worksheetSource>` or in a verbatim `rawXml` source, that names no kept relationship, with a warning.
- **Pivot tables:** `PivotCacheDefinitionData.relationships[].targetMode` is typed `'External'`; the writer reads it ignoring ASCII letter case and always writes `TargetMode="External"`. The writer skips, with a warning, a kept relationship of the `pivotCacheRecords` type (it writes that one itself) and one whose `id` is empty, does not start with an ASCII letter or `_`, or holds a character other than an ASCII letter, digit, `_`, `-` or `.`; a source `r:id` naming a skipped relationship is dropped.
- **Pivot tables:** pivot caches carry an optional `cacheId`, written to the `<pivotCaches>` list of `xl/workbook.xml`; pivot fields keep `dataField` and their subtotal flags; cache fields keep `sharedItems` attributes and `numFmtId`.
- **Charts:** `ChartSeriesData.nameLiteral` holds a literal series name, written as `c:v` when `name` is unset; `name` stays a cell-reference formula. `ChartBuilder.addSeries()` takes it as `nameLiteral`.
- **Charts:** secondary-axis combo charts keep both category axes (new `secondaryCatAxis`), and scatter and bubble charts keep both value axes (X is `valAxis`, Y is `secondaryValAxis`).
- **Charts:** new optional fields `autoTitleDeleted`, `ErrorBarsData.plusRef`/`minusRef` (custom error bar ranges), `ChartAnchorData.posX`/`posY` (an absolute anchor), `errDir` (X error bars), data-label `showLegendKey` and `showBubbleSize`, and the value axis `crossBetween`, each read and written.
- **Charts:** a chart read from a file carries `rawRels`, its own `.rels` part, and the writer places it beside the chart wherever the chart is written.
- **Charts:** `ChartBuilder.secondaryChart(builder)` makes a combo chart: the other builder's chart becomes the `secondaryChart`, drawn on this chart's axes (or on `secondaryCatAxis` and `secondaryValAxis` when the built model sets them). A nested secondary chart makes `build()` throw `RangeError`.
- **Charts:** `ChartBuilder.addSeries()` takes `idx` and `order`, the series' `c:idx` and `c:order`. `build()` numbers the series that leave them unset from 0 up, across the chart and then its secondary chart, skipping every value a series sets, so a combo chart's series get distinct orders and Excel opens it.
- **Threaded comments:** threaded comments keep `done`, `mentions` and the person's `userId`.
- **Slicers and timelines:** x14 slicer caches and x15 timelines written by Excel are read: their items, levels, pivot cache ids and bounds reach the model.
- **Hyperlinks:** `HyperlinkData.target` holds an external link's URL, written as a worksheet relationship with `TargetMode="External"`.
- **Workbook parts:** `WorkbookData.preservedContentTypes` records the content type the source package declared for each preserved part, filled by `readBuffer` and declared again on write, so parts the writer has no rule for (Office 2016 `chartEx` charts, form-control properties and the like) keep their type.
- **Workbook parts:** TypeScript types for every new wire field listed in this section, and `new Workbook(data)` keeps `calcPr`, `fileVersion`, `workbookPr` and `externalReferences`.
- **Formula engine:** the parser reads whole-column and whole-row ranges (`A:A`, `$1:$1`, `Data!B:C`), structured references (`Table1[Col]`, `[@Col]`), 3-D references (`Sheet1:Sheet3!A1`), empty arguments (`IF(A1,,2)`), the intersection operator (`A1:B5 B2:C3`) and unions (`SUM((A1,B2))`), and `serializeFormula` writes each of them back; 1.2.1 reported parse errors for all of them. New AST node types `MissingArgNode`, `ColumnRangeNode`, `RowRangeNode` and `StructuredRefNode` are exported, `CellRefNode` gains `endSheet`, and a `binary_op` node may carry `':'`, `' '` (intersection) or `','` (union).
- **Formula engine:** the tokenizer recognises `#SPILL!`, `#CALC!`, `#FIELD!`, `#BLOCKED!`, `#UNKNOWN!`, `#GETTING_DATA`, `#CONNECT!`, `#PYTHON!`, `#EXTERNAL!` and `#BUSY!`, and sheet-qualified errors such as `Sheet1!#REF!`. `TokenType` gains `'column_range'`, `'row_range'` and `'structured_ref'`, and the space intersection operator is an `operator` token with the value `' '`. Code with an exhaustive `switch` over `TokenType` or `ASTNode['type']` needs the new cases.
- **Formula engine:** the evaluator handles whole-column and whole-row references (`SUM(A:A)`; 1.2.1: `#VALUE!`), the intersection operator (`SUM(A1:C1 B:B)` reads B1, and areas that do not meet give `#NULL!`) and empty arguments (`IF(TRUE,,2)` is 0; 1.2.1: `#VALUE!`). A union where one value is expected is `#VALUE!`.
- **Formula engine:** `EvalContext` gains three optional members: `currentCell`, the cell that holds the formula (used by implicit intersection, INDEX and `ROW()`/`COLUMN()`); `dateSystem`, read by TEXT; and `getBounds`, the populated extent of a sheet, to which ranges are cut.
- **Errors:** `ModernXlsxError` accepts the standard `ErrorOptions` and keeps the underlying error as `cause`. `ModernXlsxError.code` is typed `ModernXlsxErrorCode`, a known code or any string, and the known codes are exported as the type `KnownModernXlsxErrorCode`.
- **Entry points and runtimes:** the `modern-xlsx/wasm` subpath exports the full WASM binary as a compiled module to pass to `initWasmSync()`, for Cloudflare Workers and other runtimes that import `.wasm` files that way. `modern-xlsx/browser` and `modern-xlsx/worker` ship type declarations: the `ModernXlsx` global, and the worker's message types.
- **Entry points and runtimes:** `modern-xlsx/lite` exports everything `modern-xlsx` does except the standalone barcode and drawing functions, `createXlsxWorker` and their types, so `StreamingXlsxWriter` and `PivotTableBuilder` are available there (1.2.1 lite exported neither).
- **Web Worker:** `XlsxWorker` and `StreamingXlsxWriter` implement `Symbol.dispose`, so `using` releases them. A disposed `StreamingXlsxWriter` throws `INVALID_ARGUMENT`, and calls on a terminated worker reject with `WORKER_ERROR`.
- **Builders:** `HeaderFooterBuilder.text()` escapes literal text (`&` becomes `&&`), and `HeaderFooterBuilder.fontSize(size, text)` takes the text that follows, putting a space before text that starts with a digit.
- **Builders:** `PivotFieldData` gains an optional `dataField` flag.
- **Types:** `TemporalLike` is exported; native `Temporal.PlainDate` and `Temporal.PlainDateTime` satisfy it. `ColorData`, `CalcPrData`, `FileVersionData`, `WorkbookPrData`, `MentionData`, `SharedItemsAttrs` and `SlicerPivotTable` are exported as types.
- **Barcodes:** `QrEcLevel` (`'L' | 'M' | 'Q' | 'H'`), the type of the `encodeQR` `ecLevel` option, is exported from `modern-xlsx` (not in `modern-xlsx/lite`, which has no barcode exports).

### Behaviour changes

- **Styles:** colours given as `RRGGBB`, with or without a leading `#`, are written as uppercase ARGB with an `FF` alpha, and 8-digit values are uppercased, so a font colour of `'#ff0000'` is written and read back as `'FFFF0000'`. 1.2.1 wrote the string as given, and a leading `#` produced an invalid `rgb` attribute. Chart (DrawingML) colours are unchanged.
- **Styles:** the default font of a new workbook, and of a `createStyle().font()` call without a name, is Calibri. 1.2.1 used Aptos. Pass `name: 'Aptos'` to `font()` to keep it.
- **Styles:** a colour `rgb` that is not 6 or 8 hex digits after an optional `#` (such as `'red'`), in a font, fill, border, differential-format, tab, conditional-format, sparkline or rich-text run colour, fails the write with `INVALID_WORKBOOK` naming where it sits, and `validate()` reports it as an error. 1.2.1 wrote the string into the file as given. An empty string writes no colour.
- **Workbook parts:** every written workbook contains `xl/theme/theme1.xml` with its relationship and content type. A theme read from a file is written back unchanged; otherwise the writer generates the Office theme (Calibri Light and Calibri, accent 1 `4472C4`, or your `themeColors`). 1.2.1 wrote no theme for a workbook it created.
- **Worksheets:** sheet protection follows the ECMA-376 defaults on the wire. A flag set to `false` on `SheetProtectionData` is written as `"0"` and allows that action in Excel. 1.2.1 omitted every `false` flag, so a protected sheet locked formatting, inserting, deleting, sorting and filtering whatever you set. To keep an action locked, set its flag to `true`.
- **Worksheets:** reading sheet protection applies the schema default to an absent attribute, so an absent `formatCells`, `formatColumns`, `formatRows`, `insertColumns`, `insertRows`, `insertHyperlinks`, `deleteColumns`, `deleteRows`, `sort`, `autoFilter` or `pivotTables` reads as `true` (locked), and a read and write no longer changes a sheet's protection. 1.2.1 read every absent flag it modelled as `false`.
- **Worksheets:** a `SheetProtectionData.password` that is not 1 to 4 hex digits, the legacy hash a file stores, fails the write with `INVALID_WORKBOOK` naming the sheet, and `validate()` reports it as an error in the new `sheetProtection` category. 1.2.1 wrote any string there, so a plain-text password such as `'secret'` gave a sheet that looked protected but that Excel unprotected with any password. Put the password in `plainPassword`; `password` is never hashed for you, because a password such as `'cafe'` is also a valid hash.
- **Worksheets:** `xsd:boolean` attributes in worksheets, `<col>` included, follow XML Schema exactly: `1` and `true` are true, `0` and `false` are false, and any other value (such as `TRUE`) keeps the attribute's default. 1.2.1 accepted `TRUE` for most attributes, read `false` as true for `summaryBelow`, `summaryRight`, `scaleWithDoc`, `alignWithMargins` and the sheet view flags that default to on, and read `<col collapsed="true">` as not collapsed.
- **Worksheets:** a malformed worksheet attribute (a bad number, a bad entity or character reference, or a duplicate attribute) now fails the read with `XML_PARSE`, for example `row @ht: invalid value 'abc'`. 1.2.1 used a default in its place.
- **Styles:** a malformed numeric attribute in `xl/styles.xml` (such as `numFmtId="x"`) now fails the read with `XML_PARSE`. 1.2.1 read it as 0.
- **Encryption:** a malformed or duplicate attribute in an Agile `EncryptionInfo` descriptor fails the read with `PASSWORD_PROTECTED` ("malformed EncryptionInfo"). 1.2.1 skipped the attribute.
- **Reading:** a malformed optional part no longer fails the read. Comments, tables, charts and their drawings, pivot tables, pivot caches and records, threaded comments, persons, slicers, timelines and their caches, and a worksheet's `.rels`, are left out of the model and kept verbatim in `preservedEntries`, so they survive a write. One malformed pivot part keeps all of that file's pivot tables, caches and records out of the model; every pivot part is kept. A security error in such a part still fails the read.
- **Reading:** a pivot cache definition whose `.rels` names two records parts that are both read keeps all of the file's pivot tables, caches and records out of the model, as a malformed pivot part does; 1.2.1 read both and paired them with caches by position. Give each cache definition one records part.
- **Reading:** a malformed `docProps/core.xml` drops the core properties (title, author, dates and the like), a malformed `docProps/app.xml` drops only the extended (application) properties, a malformed `xl/theme/theme1.xml` drops the theme colours and is kept verbatim and written back unchanged, and a malformed `xl/calcChain.xml` drops the calculation chain; each logs a warning and the read goes on. 1.2.1 failed the read on a parse error in these parts.
- **Reading:** a malformed character reference (such as `&#x+41;`, `&#0;`, `&#X41;` or a surrogate) in cell text, shared strings or `xl/workbook.xml` fails the read with `XML_PARSE`; in any optional part listed above (comments, tables, charts and drawings, pivot parts, threaded comments, persons, slicers, timelines) it makes that part malformed, so the part is kept verbatim as above.
- **Reading:** text read from shared strings, inline strings, cell formulas, comments and their authors, threaded comments, table formulas, chart text, defined names and document properties follows XML 1.0 line-end normalization: a literal CRLF or CR in the XML reads as LF, as any conforming XML parser reads it. 1.2.1 kept the CR. A CR written as `&#13;`, which is how modern-xlsx writes one, still reads as CR.
- **Reading:** a worksheet row cut off by the end of its part is dropped as before, but when its cells take the read JSON past `ReadOptions.limits.maxJsonLength` (the JSON is checked after each cell, see Security), the read now fails with `SIZE_LIMIT` before the row ends instead of dropping the row.
- **Reading:** `ReadOptions.limits.maxJsonLength` also bounds the memory of the elements a read keeps in its worksheet lists (data validations, conditional formats and their rules, selections, columns, hyperlinks, merged ranges, page breaks, filters, sparklines, kept extensions), added up over all the sheets of the read (with the Rust crate's `parallel` feature, which the WASM build does not use, per sheet) and counted at the size of each record in memory plus its strings. That memory is about 2 to 4 times the JSON of the same elements (4.2 times for one-rule conditional formats and 2.2 times for list data validations, natively), so a workbook can be refused with `SIZE_LIMIT` although its JSON would fit: 1,000,000 one-rule conditional formats use 92.4% of the default limit in the 64-bit Rust crate and 55.1% in the WebAssembly build, 1,000,000 list data validations 54.2% and 28.9%, 1,000,000 hyperlinks 28.3% and 17.1%, and 1,000,000 merged ranges 7.2% and 5.0%; about 1,100,000 one-rule conditional formats (JSON about 130 MB), which 1.2.1 read, now fail in the Rust crate. The WebAssembly build stores each record in about half the 64-bit size, but strings take the same bytes on both, so it keeps 1.5 to 1.9 times as many elements before `SIZE_LIMIT`. Measured at the default limit on a 1.3.0 development build of 2026-11-13 (a UTC date), the first count refused is 1,084,375 one-rule conditional formats, 1,849,609 list data validations, 3,921,875 hyperlinks and 13,839,843 merged ranges in the 64-bit Rust crate, and in the WebAssembly build of the npm package between 1,750,000 and 1,900,000 one-rule conditional formats and between 3,350,000 and 3,600,000 list data validations, all of which 1.2.1 read; 6,000,000 empty `<cfRule/>`, which 1.2.1 read in 1,990 MiB of WebAssembly memory, now fail with `SIZE_LIMIT`. 1.2.1 had no such charge. These figures were measured on 2026-11-13 (a UTC date).
- **Reading:** a styles part (`xl/styles.xml`) whose records pass the same limit in memory fails with `SIZE_LIMIT` ("the defined names, shared strings, styles, chart series and axes, threaded comments and worksheet lists take more memory than the N-byte limit"), and the style records and the worksheet list elements of one read count together. The tightest list is differential formats: at the default limit the 447,393rd empty `<dxf/>` is refused natively (1,200 bytes each on a 64-bit target) and the 684,785th in the npm (WebAssembly) build (784 bytes each), computed from the record sizes on 2026-11-13. A generous real styles part (64,000 cell formats, 10,000 fonts, fills, borders and differential formats, 2,000 number formats) uses about 6% of the limit natively and 4% in WebAssembly.
- **Reading:** the shared strings part (`xl/sharedStrings.xml`) counts against the same limit: each entry is counted at the size of its record in memory (its plain text is not counted) and each rich text run at the size of its record plus its strings, together with the style records and the worksheet lists of the read, and a table that passes the limit fails with `SIZE_LIMIT`. The first count refused in the npm (WebAssembly) build, measured on 2026-11-13 in a minimal one-sheet workbook whose only counted part is its shared strings, is 3,355,442 empty `<r></r>` runs in one `<si>`, 2,917,776 one-run entries (`<si><r></r></si>`) and 22,369,614 empty `<si/>` entries; natively, computed from the record sizes for a table that is the read's first counted part, it is 2,164,802 runs in one `<si>` and 11,184,811 empty entries. Real tables stay below the limit: 2,000,000 plain entries take 48 MB in WebAssembly (9%) and 96 MB natively (18%), and 200,000 rich entries of five runs about 181 MB (34%) and 274 MB (51%). A larger rich table can pass it: through the WebAssembly build a library-written workbook of 750,000 rich text cells of four runs each reads, and one of 875,000 or 1,000,000 fails with `SIZE_LIMIT`, where 1.2.1 reads 1,000,000 in 4.8 s (measured on 2026-11-13; see Known limitations). The limit cannot be raised past its default (V8's longest string); lowering `maxJsonLength` refuses such a part sooner. 1.2.1 had no such charge. The native counts and the shares of the limit were computed from the record sizes on 2026-11-13.
- **Reading:** chart series and axes, threaded comments and their mentions, and the workbook's defined names count against the same limit, together with the shared strings, the style records and the worksheet lists. The first count refused, each in a package of its own, is 2,164,798 empty chart series in WebAssembly (measured) and 1,398,102 natively (computed, 384 bytes each); 3,050,397 empty axes in WebAssembly and 2,485,514 natively; 6,100,794 empty threaded comments in WebAssembly and 3,050,403 natively; 4,436,941 `<definedName name="a"/>` in WebAssembly and 2,474,060 natively; and 16,777,216 empty mentions in one comment in WebAssembly and 9,586,981 natively (computed, 32 and 56 bytes each). A 306,711-byte chart of 2,242,424 empty series, which 1.2.1 read, now fails with `SIZE_LIMIT`. Real workbooks stay far below: Excel holds at most 255 series in a chart. The WebAssembly counts of series, axes, threaded comments and defined names and the 306,711-byte chart were measured on 2026-11-13; the other counts were computed from the record sizes the same day.
- **Reading:** a relationship target that starts with `//` (a network-path reference, not a part name) no longer resolves to a part of the package. 1.2.1 dropped the slashes and read `//xl/comments1.xml` as `xl/comments1.xml`.
- **Reading:** a ZIP entry whose local file header cannot be parsed fails the read with `ZIP_READ`, because the headers of entries that hold data are now read before any entry is inflated; 1.2.1 reported `ZIP_ENTRY`. An entry with no data still reports `ZIP_ENTRY`.
- **Reading:** a workbook in which two `<sheet>` entries of `xl/workbook.xml` resolve to one worksheet part (one `r:id` on two entries, or two relationships with the same target) fails the read with `SECURITY`, naming both sheets and the part, before any worksheet is parsed. 1.2.1 parsed the part once for each entry and returned two sheets with the same content. Give each sheet its own worksheet part.
- **Reading:** a part named by two sheets, two drawings or two pivot cache definitions (a comments, threaded-comments, table, slicer, timeline, drawing, chart, pivot table or pivot cache records part) is read for the first of them only; the others get nothing from it, and the reader logs one summary warning per kind of part. 1.2.1 parsed the part again for each of them, so each one got its contents. Pivot cache records read after such a shared records part keep all of the file's pivot tables, caches and records out of the model, as a malformed pivot part does. To keep the contents on every sheet, give each sheet its own part.
- **Reading:** `pivotCaches` lists the caches that have records first and the caches saved without their data after them, each group in the order of the workbook's relationships, so that `pivotCacheRecords[i]` belongs to `pivotCaches[i]`. 1.2.1 listed every cache in relationship order. Find a pivot table's cache by `cacheId`, not by position.
- **Errors:** malformed or mistyped workbook JSON passed to a write, `validate`, `repair` or `StreamingXlsxWriter.writeRow` fails with code `JSON` (constant `JSON_ERROR`). 1.2.1 reported `WASM_ERROR` (from `writeRow`, an `Error` without a code).
- **Errors:** writing a workbook without sheets (`toBuffer`, `toFile`, or `StreamingXlsxWriter.finish` before any `startSheet`) fails with `INVALID_WORKBOOK`. 1.2.1 used `INVALID_CELL_VALUE`.
- **Errors:** a write fails with `INVALID_WORKBOOK` when two pivot caches share a `cacheId`, a pivot table names a `cacheId` that no cache has, or a theme generated from `themeColors` gets a colour that is not 6 hex digits.
- **Reading:** in `modern-xlsx/lite`, a legacy `.xls` file rejects with `LEGACY_FORMAT` and an encrypted file with `PASSWORD_PROTECTED`, whose message says the lite build cannot decrypt. 1.2.1 lite reported `UNRECOGNIZED_FORMAT` for both.
- **Hyperlinks:** external links (`http:`, `https:`, `mailto:`, `file:` and other URI schemes) are read into the new `HyperlinkData.target` field, not `location`. `addHyperlink()` keeps its signature and puts a value with a URI scheme in `target`; `location` now holds an in-workbook reference, or a fragment within `target`. Code that read external URLs from `location` must read `target`. Data from 1.2.x with a URL in `location` is still written as an external link.
- **Workbook parts:** `calcChain` entries carry the 1-based position of their sheet as `sheetId` on read; 1.2.1 passed the source file's `sheetId` through. An entry without `i` belongs to the previous entry's sheet.
- **Tables and comments:** a sheet with comments is written with a VML note drawing (`xl/drawings/vmlDrawing<N>.vml`, its relationship, the `vml` content type and a `<legacyDrawing>` element), which Excel draws notes from, unless the note drawing read from the file already matches the sheet's comments, in which case it is kept byte for byte. 1.2.1 wrote the comments part alone. Reading such a file back gives the note drawing in `preservedEntries` and `preservedContentTypes`; no action is needed unless you compare written bytes or part lists.
- **Tables and comments:** `addTable` with a totals row (`totalsRowCount` of 1 or more) writes the totals cells into the last row of the table's `ref`, column by column: the `SUBTOTAL` formula Excel writes for a `totalsRowFunction` (`SUBTOTAL(109,Table1[Amount])` for `sum`; 101 `average`, 103 `count`, 102 `countNums`, 104 `max`, 105 `min`, 107 `stdDev`, 110 `var`), the column's `totalsRowFormula` for `custom`, and the `totalsRowLabel` text for a column with a label and no function. A totals cell the caller already filled is kept, and a table read from a file is not changed; Excel opens the file only if a kept cell agrees with its column (a value or the column's `SUBTOTAL` in a function column, a formula in a custom column, the label text in a label column), and `validate()` reports one that does not. 1.2.1 wrote only the table definition, so the workbook gains cells (different bytes); fill a totals cell before `addTable` to keep your own value.
- **Tables and comments:** `addTable` throws `ModernXlsxError` `INVALID_ARGUMENT` for a table name Excel refuses to open: a display name that is empty, longer than 255 UTF-16 code units, holds a space, tab, line break, DEL or ASCII punctuation other than `_ . \ ?`, starts with a digit, `.`, `?` or a combining mark (U+0301 + `abc`, U+093F + `x`; a leading Thai mark such as U+0E34, which Excel opens, is refused too), is `TRUE` or `FALSE`, is a cell reference in the grid (`T2`, `Q1`) or an R1C1 reference or starts with one (`R`, `C`, `RC`, `R1x`; the R1C1 letters were checked against English-language Excel), or that another table's display name or a defined name already has; or a `name` longer than 255 code units or that another table's `name` already has (case and canonical equivalence ignored throughout). The sheet is unchanged then. 1.2.1 wrote these files without error, and Excel refused them.
- **Tables and comments:** `addTable` throws `ModernXlsxError` `INVALID_ARGUMENT` for a `calculatedColumnFormula` or `totalsRowFormula` that holds the `@` this-row shorthand (`[@Qty]`, `[@[Unit Cost]]`, `Sales[@Qty]`, `[@]`) outside string literals and quoted names, and the message gives the form Excel writes in a file: for `calculatedColumnFormula: '[@Qty]*[@Price]'` in table `Sales` it says to write `Sales[[#This Row],[Qty]]`. The formulas are not rewritten. A `[@...]` that names a column of the table (a column called `@Home`, referenced as `Sales[@Home]`, as Excel writes it) is a column reference and is accepted. The names are compared after the `_xHHHH_` escapes of the table part are decoded on both sides, and a `[@...]` of a table in another workbook (`[1]!Ext[@Home]`, which Excel stores for `Book.xlsx!Ext[@Home]`) is not checked. A formula that names a table in another canonical form (`Cafe` + U+0301 for `Café`) names that table, so a `[@...]` naming one of its columns passes. 1.2.1 wrote the shorthand as given, and Excel refused the file.
- **Tables and comments:** `validate()` reports, as errors in the `structure` category, the table names `addTable` refuses (except a name canonically equivalent to another table or defined name and a name that starts with a combining mark, see Known limitations), a `calculatedColumnFormula` or `totalsRowFormula` that holds the `@` shorthand `addTable` refuses, and a totals-row cell Excel refuses to open: a formula other than the column's `SUBTOTAL` in a function column, no formula in a `custom` column that has a `totalsRowFormula`, and a formula, a number, a boolean or text other than the `totalsRowLabel` in a column without a function. A workbook holding such a table, which validated in 1.2.1, now reports an error; its file never opened in Excel. A value that is not a comma-separated list of cell references, ranges, column spans or row spans throws `ModernXlsxError` `INVALID_ARGUMENT`. `addNamedRange` stores `_xlnm.Print_Area` and `_xlnm.Print_Titles` given in another letter case (`'_xlnm.print_area'`) in the spelling Excel writes. `validate()` reports a `_xlnm.Print_Area` or `_xlnm.Print_Titles` defined name, in any letter case, whose area has no sheet qualifier as an error (category `definedName`), so a workbook read from a 1.2.x file with such a name now gets `isValid` false. 1.2.1 stored the value as given, and Excel refused a file whose print area or print titles had no sheet name. Compare `getPrintArea` and `getPrintTitles` results with the qualified form.
- **Workbook and worksheet API:** setting `worksheet.name` on a sheet of a workbook renames it through `renameSheet`, so `getSheet` finds the new name (1.2.1: `undefined`), a duplicate name is rejected and defined names follow.
- **Workbook and worksheet API:** `renameSheet` (and the `Worksheet.name` setter) rewrites references to the sheet in defined names, print areas and print titles to text that resolves to the same reference as Excel's own rename, quoting the new name when needed: `Sheet1!$A$1:$A$3` becomes `Data!$A$1:$A$3`, and an end of a 3-D span follows too (`Sheet1:Sheet3!A1` becomes `Data:Sheet3!A1`). The text is not always spelled as Excel spells it: a non-ASCII new name is quoted (`'Données'!$A$1`, where Excel stores `Données!$A$1`), and `Sheet1:Sheet1!$A$1` becomes `Data:Data!$A$1` (Excel stores `Data!$A$1`). A quoted prefix that holds a colon is rewritten as a 3-D span only when both ends are sheets of the workbook, as Excel 365 does; otherwise Excel reads it as a path into another workbook and it is kept as it is: with sheets `Sheet1` and `C`, `'C:/dir/Book.xlsx'!A1`, `'Sheet1:Nosuch'!$A$1`, `'Nosuch:Sheet1'!$A$1`, `'C:Nosuch'!$A$1`, `'Sheet1:''x'!$A$1` and `'Sheet1:x'''!$A$1` are kept. Only a quoted colon prefix is read as such a path: an unquoted prefix whose first end is no sheet (`First:Sheet1!$C$10`, a name, the range operator and a sheet-qualified reference) has its last end follow the rename, as in Excel's own rename, so `First:Sheet1!$C$10` becomes `First:'Data'!$C$10` and `SUM(Nosuch:Sheet1!$A$1)` becomes `SUM(Nosuch:'Data'!$A$1)`. A rewritten sheet name right after the range operator is quoted, as Excel 365 stores it (build 20527, read from the files it saved on 2026-11-14): `Other!$A$1:Sheet1!$B$2` becomes `Other!$A$1:'Data'!$B$2`, and renaming Sheet1 to `First` beside a defined name `First` turns `First:Sheet1!$C$10` into `First:'First'!$C$10`, which Excel reads as the name joined to `First!$C$10`, where the unquoted `First:First!$C$10` would be the one-sheet span `First!$C$10`. Renaming another sheet to `First` quotes the sheet after `First:` for the same reason (`First:Sheet1!$C$10` becomes `First:'Sheet1'!$C$10`). Excel 365 computes the same values from the library's renamed files as from its own (2026-11-14). A sheet prefix is matched ignoring case with the Greek final sigma folded, as Excel 365's own rename matches it: renaming sheet `ΟΔΟΣ` to `X` also rewrites `οδοσ!$A$2` and `SUM(οδοσ:Other!$A$1)`, and a prefix that spells U+0130 (capital I with dot above) as `i` + U+0307 is kept for a sheet named with U+0130, as Excel keeps it. A reference into another workbook that shares the sheet's name (`[1]Sheet1!$A$1`) keeps naming that workbook's sheet, as do text in string literals and longer sheet names (`Sheet10`). A value the formula tokenizer rejects, such as one with a sheet-qualified defined name (`Sheet1!myName`), is left unchanged. The rewrite takes time linear in the length of each value (100,000 references in one value take well under a second). On hand-built data that holds a sheet whose name is not a string, the rename completes and that sheet matches no prefix. 1.2.1 kept every `Sheet1!`. Cell formulas, chart series, pivot cache sources, data validations, conditional formats and hyperlinks are not rewritten (see Known limitations). A rename does not check the defined names the workbook holds: a name Excel saved with a combining mark or a symbol (`a€b`) keeps its text, and only its references to the sheet are rewritten.
- **Workbook and worksheet API:** `addNamedRange` checks the name, the `sheetId`, and that the name is unique in its scope, ignoring case and canonical equivalence (`café` with U+00E9 repeats `cafe` + U+0301), and throws `ModernXlsxError` `INVALID_ARGUMENT` for a name that is not 1 to 255 characters, does not start with a letter, `_` or `\`, has a later character other than a letter, combining mark, digit, `_`, `.`, `\` or `?` (`a?b` and `cafe` + U+0301 are accepted), is `TRUE` or `FALSE`, is a cell reference in the grid (`A1`; `XFE1`, `A0` and `R1048577` lie outside it and are accepted), is an R1C1 reference or starts with one (`R2D2`, `C1_total`, `R1x`; `R1.a` is accepted; the R1C1 letters were checked against English-language Excel), uses `_xlnm.` for anything but `Print_Area`, `Print_Titles` and `_FilterDatabase`, or that a table on any sheet already has, compared the same way (the mirror of the check `addTable` makes). `addTable` compares a new display name with every table and defined name, and a new `name` with every table's `name`, the same way, and `cloneSheet` gives a copied table a name no table or defined name has under that comparison. `addNamedRange('A1', ...)` throws, and so does `addNamedRange('sales', ...)` after `addTable({ displayName: 'Sales', ... })`, and `addTable({ displayName: 'cafe\u0301', ... })` after `addNamedRange('caf\u00e9', ...)`. 1.2.1 accepted every name, and Excel refused a file holding an R1C1-shaped name, `TRUE` or `FALSE`, or a name a table has.
- **Workbook and worksheet API:** `validate()` reports, as an error in the `definedName` category, a defined name Excel refuses to open: an R1C1 reference or a name that starts with one, `TRUE` or `FALSE`, a character Excel refuses, a leading digit, `.` or `?`, or more than 255 characters (`_xlnm.` names are not checked), for example "Invalid defined name 'R2D2': it is an R1C1 reference or starts with one". A workbook read from a file holding such a name now gets `isValid` false; Excel refuses that file. 1.2.1 reported none of these.
- **Workbook and worksheet API:** `moveSheet` with an out-of-range target throws "Invalid target index: 9" (1.2.1: "Invalid destination index: 9").
- **Workbook and worksheet API:** a formula cell takes the type of its cached value: `Cell.type` is `'number'` for a number or no value, `'boolean'` for a boolean and `'formulaStr'` for text, so a formula over a cached 5 reports `'number'` (1.2.1: `'formulaStr'`). Clearing the formula of a `'formulaStr'` cell gives `'sharedString'`, or `'number'` when it holds no value.
- **Workbook and worksheet API:** setting `cell.value` or `cell.richText` on a shared-formula child (a cell without formula text in a filled-down group) replaces its formula: `formulaType`, `formulaRef` and `sharedIndex` are removed and the cell is written as a plain value or shared string. This holds for every writer that goes through the value setter, so values that `drawTable`, `drawTableFromData`, `sheetAddAoa` or `sheetAddJson` write over a shared-formula child replace its formula too; a master keeps its formula, and the value becomes its cached result. In 1.2.1 the child kept `<f t="shared" si>`: Excel recalculated the group formula over a value, and showed the group formula in place of rich text. `cell.value = null` on a child writes an empty cell, as in 1.2.1.
- **Workbook and worksheet API:** setting `cell.formula` to new text on a shared-formula child (a cell with `formulaType` `'shared'` or a `sharedIndex` and no `formulaRef`, whether or not it carries formula text of its own) gives that child a plain formula of its own: its shared keys are removed and it is written as `<f>text</f>`. In 1.2.1 the child kept its keys and was written `<f t="shared" si="N">text</f>`, so Excel ignored the text and showed the group formula, or refused the file when the group's master had been cleared. New text on a master (a cell with a `formulaRef`) keeps its keys, as in 1.2.1.
- **Workbook and worksheet API:** `cell.formula = null` or `''` also removes `formulaType`, `formulaRef` and `sharedIndex`, and `''` clears the formula as `null` does: `cell.formula` then returns `null` and the cell is written without `<f>`. In 1.2.1 the keys stayed on the cell model, and `''` was kept and written as an empty `<f></f>`.
- **Workbook and worksheet API:** `validate()` and `repair()` return a bounded report: `issues` holds the first issues found, at most 10,000 of them and at most 16 MiB of message and location text. `errorCount`, `warningCount`, `infoCount` and `isValid` still count every issue, and the new optional `omittedIssueCount` says how many were left out (absent when none). 1.2.1 stored every issue.
- **Workbook and worksheet API:** setting a cell to `NaN` or an infinite number, directly or through `aoaToSheet` or `jsonToSheet`, throws `ModernXlsxError` `INVALID_CELL_VALUE` (1.2.1 stored `NaN`).
- **Workbook and worksheet API:** `Cell.dateValue` uses the workbook's date system: serial 0 in a 1904 workbook is 1904-01-01 (1.2.1: 1899-12-31).
- **Builders:** `drawTable` with `autoFilter` filters the header and every data row: a two-row table at C5 gets `C5:D7` (1.2.1: `C5:D5`).
- **Builders:** `drawTable` with `freezeHeader` freezes the rows through the header row at any origin: 5 rows for a table at C5 (1.2.1: always 1 row).
- **Builders:** `drawTable` writes `Date` cells as date serials with the `yyyy-mm-dd` format (1.2.1 left them empty), and accepts `bigint` cells, written as a number when they are a safe integer and as text otherwise.
- **Builders:** `drawTable` with no headers throws `RangeError` (1.2.1 returned the invalid range `A1:@1`), and `drawTableFromData` with no data and no `headers` option returns an empty range (`range: ''`, `rowCount: 0`) without touching the sheet (1.2.1: `A1:@1`).
- **Builders:** `RichTextBuilder.build()` returns a frozen copy (1.2.1: a mutable array).
- **Builders:** `PivotTableBuilder.addDataField` marks its pivot field with `dataField: true`; 1.2.1 put the field on the values axis (`axis: 'axisValues'`) and copied the data field's name into it. A field index that is not an integer from 0 to 16,383, or a row, column or page field that is already on an axis, throws `RangeError`.
- **Builders:** `StyleBuilder.build` reuses a font, fill, border or cell format equal to one the workbook already holds, so building the same style twice returns the same style index. 1.2.1 appended new records on every build. Code that edits a built style's records in place now changes every cell that shares them.
- **Builders:** `HeaderFooterBuilder.build()` throws `RangeError` for a string longer than the 255 characters Excel allows (1.2.1 returned it), `HeaderFooterBuilder.color()` for a colour that is not 6 or 8 hex digits, and `HeaderFooterBuilder.fontSize()` for a size that is not an integer from 1 to 409.
- **Charts (TypeScript):** `ChartBuilder.addSeries({ lineWidth })` takes points and stores EMU (12,700 per point), so 2 is stored as 25400 (1.2.1 stored 2). A width that is not a finite number from 0 to 1584 points throws `RangeError`.
- **Charts (TypeScript):** `ChartBuilder.build()` returns a deep copy, so later builder calls do not change a chart already built.
- **Charts (TypeScript):** `validateChartData` enforces the ECMA-376 ranges (`styleId` 1-48, font sizes, trendline order and period, anchor order, an axis `logBase` from 2 to 1000, and a `majorUnit` or `minorUnit` greater than 0), and throws `RangeError` for an empty `valRef` and for a series fill or line colour, chart title colour or axis title colour that is not six hex digits `RRGGBB`.
- **Charts (TypeScript):** `getChartStylePalette` throws `RangeError` for any style other than 1-8; styles 9-48 have no bundled palette (1.2.1 returned the default palette for any unknown style, including 0 and 49); styles 1-8 are unchanged.
- **Charts (TypeScript):** `ChartBuilder` always writes both axes of a chart type that has axes: a line chart built without `catAxis()` or `valAxis()` gets axis ids 0 and 1 (1.2.1 wrote neither axis), and one built with only `catAxis()` gets its value axis too (1.2.1 left it out).
- **Charts:** a chart two of whose series share an `order` (`c:order`), within one chart-type element or across the chart and its `secondaryChart`, fails the write with `INVALID_WORKBOOK` naming the sheet, the chart and both series, `validate()` reports it as an error, and `validateChartData` (run by `addChart` and `addChartData`) throws `RangeError`. 1.2.1 wrote such a chart, and Excel refuses to open it; a combo chart put together from two `ChartBuilder.build()` results, whose series are both numbered from 0, is one. - **Utilities and CLI:** `sheetToCsv` and `sheetToTxt` quote a field that contains a carriage return (1.2.1 wrote it unquoted).
- **Utilities and CLI:** `sheetToCsv`, `sheetToTxt` and `sheetToHtml` write `TRUE` and `FALSE` for boolean cells, as Excel does; 1.2.1 wrote `1` and `0`. `modern-xlsx convert --format csv` writes them the same way, and `sheetToJson` still returns `true` and `false`.
- **Utilities and CLI:** `jsonToSheet`, `sheetAddJson`, `aoaToSheet` and `sheetAddAoa` write a `Date` as ISO 8601 UTC text (`toISOString()`, such as `2024-01-01T00:00:00.000Z`) and skip an invalid `Date`. 1.2.1 wrote `String(date)`, which depends on the host's time zone.
- **Utilities and CLI:** `jsonToSheet` and `sheetAddJson` write the value under an empty-string key (`''`); 1.2.1 skipped it.
- **Utilities and CLI:** the `modern-xlsx` command exits with 0 on success, 1 on a runtime failure and 2 on a usage error, and prints `modern-xlsx: <message>` without a stack trace; `--format` must be `csv` or `json` (`--format xml` exits with 2) and `--sheet` is checked. 1.2.1 `info` and `convert` failed with `WASM_INIT_FAILED` and a stack trace.
- **Barcodes:** `renderBarcodePNG`, `generateBarcode` and `addBarcode` write 1-bit palette PNGs (1.2.1: 8-bit RGB); colours are unchanged.
- **Barcodes:** `renderBarcodePNG`, `generateBarcode` and `Workbook#addBarcode` throw `RangeError` when a `foreground` or `background` channel is not an integer from 0 to 255; 1.2.1 wrapped it silently.

A rejected `addImage` leaves the workbook unchanged. 1.2.1 wrote such anchors.

- **Build and dependencies:** the Rust toolchain is pinned to the dated nightly `nightly-2026-11-14` (`rust-toolchain.toml`); 1.2.1 tracked the beta channel. The minimum supported Rust version stays 1.96.0.

### Deprecated

- **Worksheets:** `CellData.dynamicArray`, `formulaDtr1` and `formulaDtr2` are deprecated and will be removed in 2.0; use `cellMetadata`, `formulaDel1` and `formulaDel2`.

### Removed

- **Build and dependencies:** the generated `packages/modern-xlsx/wasm/` and `wasm-lite/` files are no longer committed to the repository; `pnpm build:wasm` and `pnpm build:wasm:lite` build them. The npm package still ships both.

### Fixed

- **Encryption:** password-protected workbooks saved by Excel (Agile, AES-256 with SHA-512) open. 1.2.1 failed on them with "AES decryption failed (bad padding)", and could not read the MS-CFB mini stream that holds their `EncryptionInfo`.
- **Encryption:** Standard-encrypted files (Office 2007, AES-128) decrypt: the key derivation and the package cipher (AES-ECB) follow MS-OFFCRYPTO.
- **Encryption:** files written with `toBuffer({ password })` or `toFile(path, { password })` use the MS-OFFCRYPTO field lengths and `dataIntegrity` HMAC, so Excel and other MS-OFFCRYPTO readers verify them. Files written by 1.2.x still open.
- **Encryption:** encrypting a large workbook no longer fails with an error naming a false "~3.5 GB" limit: the OLE2 writer emits DIFAT sectors, and the only remaining cap is MS-CFB version 3's 2 GiB per stream (`SIZE_LIMIT`).
- **Encryption:** large encrypted files are no longer truncated on read: the reader follows the DIFAT chain past the 109 FAT sectors the header lists.
- **Encryption:** version 4 compound files (4096-byte sectors) are read at the right offsets.
- **Encryption:** Standard `EncryptionInfo` is parsed at the spec offsets; 1.2.1 skipped the `EncryptionVerifier` `SaltSize` field.
- **Encryption:** RC4 CryptoAPI, ciphers other than AES, `ChainingModeCFB` and unsupported key sizes or hash algorithms report "unsupported encryption: ..." instead of "Incorrect password.".
- **Encryption:** a certificate key encryptor listed in an Agile file no longer overrides the password key encryptor.
- **Encryption:** Agile files whose password key encryptor uses a `saltSize` other than 16, or a `keyBits` different from the `keyData` `keyBits`, open.
- **Encryption:** `EncryptionInfo` attribute values are normalized as XML requires (character references, tabs), so conformant descriptors from other producers read.

- **Formula engine:** ROWS and COLUMNS of a whole column or row return 1,048,576 and 16,384 (`ROWS(A:A)`, `COLUMNS(1:1)`) and `ROW(A:A)` is 1; ROW of a range written bottom-up (`ROW(A5:A1)`) is its top row; and ROW, ROWS and COLUMNS accept an intersection (`ROWS(A1:B5 B2:C3)` is 2).
- **Formula engine:** formulas with non-ASCII defined names or unquoted non-ASCII sheet names (`Données!A1`, `Лист2!A1*2`, `売上+1`) tokenize, so they evaluate, `rewriteFormula` and `expandSharedFormula` shift them (writing the sheet prefix quoted), and `renameSheet` rewrites defined names that use them.
- **Formula engine:** `rewriteFormula` matches `action.sheet` against sheet prefixes without regard to case, as Excel does: `sheet1!A5` shifts for `sheet: 'Sheet1'`.
- **Formula engine:** a range with a function or chained endpoint (`SUM(A2:INDEX(A:A,B1))`, `OFFSET(A1,1,1):B5`, `A1:B1:C1`) parses, so `rewriteFormula` and `expandSharedFormula` shift it instead of returning the formula unchanged. Evaluating a function endpoint still gives `#VALUE!`.
- **Formula engine:** a range with a `#REF!` endpoint (`SUM(#REF!:C2)`, as Excel writes one after a delete, and as `rewriteFormula` writes when a chained range loses an endpoint) parses, evaluates to `#REF!` and is still shifted by `rewriteFormula`; 1.2.1 reported a parse error. Other error values as endpoints (`SUM(#N/A:C2)`) are still parse errors.
- **Formula engine:** long operator chains within Excel's 8,192-character limit (`1+1+...+1`, `A1&...`, `A1%%...`, a 2,700-area union in `SUM((A1,A1,...))`) evaluate instead of returning `#NUM!`, and `expandSharedFormula`, `rewriteFormula` and `serializeFormula` no longer throw `RangeError` on them.
- **Number formats and dates:** a format with more than 100 decimal places keeps them instead of throwing `RangeError`.
- **Number formats and dates:** `y` and `yy` show the two-digit year, `yyy` and `yyyyy` the four-digit year, and any run of `e` the year.
- **Number formats and dates:** the `A/P` and `a/p` token switches the hour to the 12-hour clock and shows `A` or `P` in the letter case of the code.
- **Number formats and dates:** an escaped `\;`, or a `;` after `_` or `*`, no longer splits sections: `'0\;0'` shows 5 as `0;5`.
- **Number formats and dates:** `[Red]` or `[>5]` inside quotes is literal text, not a colour or a condition: `'"[Red]"0'` shows 5 as `[Red]5`.
- **Number formats and dates:** `formatCell(value, id)` renders the built-in CJK date ids 27-36, 50-55, 57 and 58 with the code of id 14 instead of General.
- **Workbook and worksheet API:** setting a cell's value clears its old rich text; 1.2.1 kept the old runs.
- **Workbook and worksheet API:** a print area or print titles set without a sheet name (`setPrintArea('A1:B2')`) no longer makes Excel refuse the whole file: the area is stored qualified with the sheet's name (see Behaviour changes), and `validate()` reports an unqualified one. 1.2.1 had the defect.
- **Workbook and worksheet API:** `_xlnm.Print_Area` and `_xlnm.Print_Titles` spelled in another letter case are recognised everywhere, as Excel recognises them: `addNamedRange('_xlnm.Print_area', 'A1:B2', 0)` stores a sheet-qualified value under the spelling `_xlnm.Print_Area`, and `getPrintArea`, `setPrintArea`, `getPrintTitles` and `setPrintTitles` read and update such an entry instead of returning `null` or adding a second one. Of several entries of one built-in name on a sheet they read the last, which Excel uses, and a set leaves one entry. 1.2.1 stored the variant as given, `getPrintArea` returned `null` for it, and `setPrintArea` added a second entry.
- **Workbook and worksheet API:** `removeSheet`, `moveSheet` and `cloneSheet` with an insert index remap sheet-scoped defined names (print areas and titles included) and the workbook view's `activeTab` and `firstSheet`. Names scoped to a removed sheet are dropped, and the calculation chain is dropped when sheet positions change, for Excel to rebuild.
- **Workbook and worksheet API:** `cloneSheet` rejects an insert index that is not an integer from 0 to the sheet count, and gives cloned tables and threaded comments new ids that are unique in the workbook (tables become `Name_2`, `Name_3` and so on, the name cut so that it stays within 255 UTF-16 units without splitting a surrogate pair, with a `_` before a cut name that would be an R1C1 reference: a 255-unit `R0...01.a` clones to `_R0...0_2`, not `R0...01_2`, which `addTable` refuses and Excel does not open).
- **Workbook and worksheet API:** `cloneSheet` of a sheet whose table has a totals row (written by `addTable`, or read from a file) no longer gives a file Excel refuses: structured references to a cloned table in the copy's cell formulas, totals row included, and in its calculated-column and custom totals formulas name the copy's renamed table, also when the formula spells the table name in another case or normal form (`cafe` + U+0301 + `[Qty]` for table `café`), as Excel's own copy does, for every table name Excel accepts (`a\b`, `a?b` and `Ventes€` included), and a formula with many such references is rewritten in time linear in its length. Formulas on other sheets and defined names keep naming the source table, and so does a formula that also holds another name the formula engine cannot read (see Known limitations). 1.2.1 refused every cloned table for another reason (the clone kept the source table's name and id).
- **Workbook and worksheet API:** `Cell.numberFormat` prefers the workbook's own number formats, and a built-in date id that has no code in the built-in table resolves to the code of id 14.
- **Workbook and worksheet API:** `removeSheet`, `removeChart`, `removePivotTable`, `removeSlicer` and `removeTimeline` return `false` for a `NaN` or fractional index instead of removing the first item.
- **Workbook and worksheet API:** a sheet or table name held as a `String` object (hand-built data, outside the types) is compared by its string value, so `addSheet('Data')` beside a sheet named `new String('Data')` is refused; 1.2.1 accepted it and wrote two sheets `Data`, which Excel refuses to open.
- **Workbook and worksheet API:** cells stay in column order; `setColumnWidth`, `groupColumns` and `ungroupColumns` split a multi-column span instead of duplicating it; and `addImage` no longer overwrites images already in `xl/media`.
- **Builders:** in `drawTable`, `columns[c].header` overrides `headers[c]`, and a width from `columnWidths` or `columns[c].width` wins over `autoWidth` for that column.
- **Builders:** `PivotTableBuilder.build()` returns an independent copy, so later builder calls no longer change a pivot table already built.
- **Builders:** `ChartBuilder` data labels keep `showLegendKey` and `showBubbleSize`.
- **Builders:** `drawTableFromData` treats data keys such as `constructor` as ordinary keys: a record without its own value for one gets an empty cell, not the inherited `Object.prototype` member. A getter or other member of the record's own class still supplies the value, as in 1.2.1, unless its name is also an `Object.prototype` member (such as `toString`).
- **Builders:** `StyleBuilder.build` no longer throws `RangeError` on a workbook with very many custom number formats.
- **Utilities and CLI:** `jsonToSheet` and `sheetAddJson` no longer write an inherited `Object.prototype` member into a cell for a record that lacks the key (1.2.1 wrote `function Object() { [native code] }` under a `constructor` header).
- **Barcodes:** QR codes carry the second copy of the format information where ISO/IEC 18004 puts it, so decoders that fall back to it read the symbol.
- **Barcodes:** QR codes at version 6 with error-correction level Q use the standard block structure (4 blocks of 19 data codewords); such symbols did not scan in 1.2.1.
- **Barcodes:** Code 39 encodes the space, `/` and `%` with their standard patterns; in 1.2.1 a space did not scan and `/` and `%` scanned as each other.
- **Barcodes:** Code 128 symbols that mix letters with runs of four or more digits carry the right check character.
- **Barcodes:** `encodeUPCA` checks a given 12th check digit (1.2.1 encoded `'123456789013'`); UPC-A and ITF-14 reject non-digit input with an "only digits" message, as EAN-13 already did (1.2.1 UPC-A encoded `'12345678901a'`, and ITF-14 reported an invalid check digit); and `encodeCode39('')` throws "Code 39: data must not be empty" (1.2.1 encoded an empty symbol).
- **Barcodes:** GS1-128 parses Application Identifiers, checks fixed-length ones and inserts FNC1 separators.
- **Barcodes:** Data Matrix padding no longer emits a zero codeword, and text beyond Latin-1 is encoded as UTF-8 through ECI.
- **Barcodes:** PDF417 throws "data too long" past its capacity, and a non-finite `ecLevel` or `columns` throws `RangeError`; `moduleSize`, `quietZone`, `fitWidth` and `fitHeight` are checked (`RangeError`); and the caption font draws `$`, `+` and `%`.
- **Entry points and runtimes:** `await initWasm()` with no argument works on Node.js for `modern-xlsx` and `modern-xlsx/lite`, reading the WASM binary from the package; 1.2.1 rejected with "fetch failed".
- **Entry points and runtimes:** browser bundles hold no `node:` imports (#24); the 1.2.1 IIFE imported `node:fs/promises`.
- **Entry points and runtimes:** the IIFE records its script URL when it loads, so `ModernXlsx.initWasm()` called from a later script finds `modern-xlsx.wasm` beside the bundle, or else against the document base URL.
- **Entry points and runtimes:** `modern-xlsx/lite` writes, validates and repairs through the lite WASM build, and its bundle no longer contains the full WASM glue. 1.2.1 lite threw `WASM_INIT_FAILED` from `toBuffer`, `validate` and `repair` unless the full build was also initialized.
- **Entry points and runtimes:** `initWasm()` no longer logs wasm-bindgen's "using deprecated parameters for the initialization function" warning.
- **Entry points and runtimes:** the package manifest names the author, the repository directory and the bugs URL.
- **Errors:** `ModernXlsxError.fromWasmError` keeps the code of a `[CODE] message` whose message spans lines, such as one naming a sheet or ZIP entry with a newline, instead of reporting `WASM_ERROR`.
- **Web Worker:** a relative `wasmUrl` resolves against the page, errors from the worker keep their codes, a WASM initialization failure inside the worker rejects with `WASM_INIT_FAILED`, a message that cannot be deserialised rejects the pending calls with `WORKER_ERROR`, and `readBuffer` copies a view on part of a buffer instead of detaching the caller's buffer.
- **Utilities and CLI:** a header or sheet named `__proto__` stays an ordinary key in `sheetToJson` output.
- **Examples:** the encrypted-payroll example hides its bonus and net-pay formulas under sheet protection and allows sorting and filtering on the protected sheet, and its average salary is total salary divided by total headcount; the CSV example parses RFC 4180 input (quoted fields, doubled quotes, CRLF or LF line ends, line breaks inside quotes) and keeps decimals with the `'#,##0.0#'` format; the Node examples use `toFile` and `columnToLetter`, and the CSV example `dateToSerial`; the demo site accepts `.xlsx` files only; and every example pins `modern-xlsx` exactly.
- **Examples:** the React, Vue, Svelte and Angular snippets are fixed: Svelte readiness is reactive, React column widths are 1-based, every helper and component shows an initialization error, Angular uses `inject()` without the `standalone` flag, and Vue destructures its props reactively.
- **Examples:** the encrypted-payroll example gives both sheets the same protection settings, and the comments of the encrypted-payroll and sales-report examples match their code.
- **Examples:** the service-worker example registers as a classic worker and loads the IIFE bundle with `importScripts()`; 1.2.1 imported the WASM glue as an ES module. CI runs it in Chromium against the built package. A failed WASM load no longer breaks every later request: the worker answers 500 and retries the load on the next request.
- **Examples:** chart series names use `nameLiteral`, so Excel shows the legend text; the browser demo site has an accessible loading overlay, live status, file input name, focus ring and reduced-motion support; and the Vue, Svelte and Angular export components reuse their `downloadBlob` helper.

### Known limitations

- **Slicers and timelines:** the writer emits slicers and timelines in a custom dialect that Excel has not verified, without the `extLst`, defined-name and drawing links Excel needs to load them, and a slicer or timeline read from an Excel file is rewritten in that dialect on write. Alignment with MS-XLSX is planned for 1.9.0.
- **Workbook parts:** the x14 `slicerCaches` and x15 `timelineCacheRefs` lists of the workbook `<extLst>` are neither read nor written, and the workbook `<extLst>` is not kept.
- **Reading:** a read builds the whole workbook as one JSON string, so a workbook whose JSON would pass `maxJsonLength` (at most V8's maximum string length) cannot be read; a streaming read is planned for 1.4.0 (#31).
- **Reading:** the memory charge of rich shared strings (see Behaviour changes) refuses a large rich table that 1.2.1 read: through the WebAssembly build a library-written workbook of 765,000 or more rich text cells of four runs each (bold, italic, red and plain, each with its own text) fails with `SIZE_LIMIT`, and 760,000 read in 3.7 s (measured on 2026-11-14 at the default limits, with the release branch's build); the first refused count depends on the runs' formatting, and 1.2.1 reads 1,000,000 such cells in 4.8 s (measured on 2026-11-13). The limit cannot be raised, because the default of `maxJsonLength` is also its ceiling. The streaming read and a smaller run record, planned for 1.4.0, lift it.
- **Reading:** `XlsxWorker.readBuffer` takes `password` only, not `limits`; limits for the worker are planned for 1.4.0, with the streaming read.
- **Reading:** the shared text a read copies (see Security) is counted when it is copied, so copies that never reach the result count all the same while their part is read: a comments part that later turns out malformed (it is then kept verbatim and its notes dropped), and the cells of a last row cut off by the end of its worksheet part (the row is dropped). Such a part fails the read with `SIZE_LIMIT` when its copies alone pass `maxJsonLength`, instead of being dropped; under the limit their count is given back. With the Rust crate's `parallel` feature (not in the WASM build) the limit holds per sheet while sheets parse, and across sheets once all are parsed. The memory of the records a read keeps (see Behaviour changes) is held to the limit per sheet under that feature, each sheet's lists together with the records counted before the sheets (defined names, shared strings, style records, chart series and axes, threaded comments), so the sheets of one read can together keep up to their number times it. A crafted shared-string cell with several `<v>` counts, on the JSON path of `readBuffer`, the runs of the rich entry each `<v>` names, though it keeps the runs of its last `<v>` only (see Behaviour changes), so such cells reach `SIZE_LIMIT` sooner there than through the Rust crate's `read_xlsx`, which counts the last only; a cell with one `<v>` counts the same on both.
- **Reading:** a worksheet, drawing, chart or other part the reader finds through a relationship target is looked up by its exact name: a package whose relationship names `xl/worksheets/sheet1.xml` while the part is stored as `xl/worksheets/Sheet1.xml` fails to read with `MISSING_PART` (Excel opens it). The shared strings and styles parts are read from their fixed names (`xl/sharedStrings.xml` and `xl/styles.xml`, in any ASCII letter case), not through the workbook's relationships, so a package whose relationship names another shared strings part (`xl/sst.xml`) reads every shared-string cell as its index, as 1.2.1 did. Resolving both through the relationships is planned for 1.4.0.
- **Reading:** a fixed-name part stored in another letter case is read, but its entry in `preservedContentTypes` loses the type its package declares for it: a theme stored as `xl/theme/Theme1.xml` gets `application/xml`, not the theme content type. The writer types the theme itself, so the written file is the same. Keeping the declared type is planned for 1.4.0, with the lookup through relationships.
- **Drawings and images:** when a sheet with charts has a preserved drawing that is not valid UTF-8, not well-formed XML, or has a malformed `.rels`, the write keeps only the charts and logs a warning; that drawing's pictures and shapes are not written, as in 1.2.1.
- **Charts:** 3-D, surface, bar-of-pie and pie-of-pie charts are kept verbatim in `rawXml` but not modelled, and edits to their model have no effect while `rawXml` is set; modelling them is planned for 1.8.0.
- **Pivot tables:** the `showAll`, `sortType` and `numFmtId` attributes of `<pivotField>`, the `rowItems` and `colItems` layout caches and `pivotTableStyleInfo` are not kept through a read and write; keeping them is planned for 1.9.0.
- **Pivot tables:** the writer does not compute a pivot table's layout or cell values. A table built in code shows its values once Excel refreshes it on open; read back and written again by modern-xlsx without Excel in between, it shows them after a refresh.
- **Pivot tables:** a cache field with number or date shared items needs its `sharedItemsAttrs` (`containsNumber`, `containsString: false` and the like) set as Excel writes them; without them Excel refuses the file.
- **Pivot tables:** a pivot table with a page field read from an Excel file, or one over multiple consolidation ranges, loses its location's `rowPageCount` and `colPageCount`, which are not modelled. The file opens with the table's values, but after a Refresh Excel shows `#SPILL!` in place of the table.
- **Pivot tables:** the `id` of a kept pivot cache relationship is not length-limited: a very long, highly repetitive id (1 MB of one letter) gives a `.rels` part that deflates past the default `maxCompressionRatio`, so reading the written file fails with `SECURITY`, as it does for any such run of text. Limiting the length of a kept relationship id is planned for 1.9.0.
- **Threaded comments:** a placeholder note read from a file is kept as it is, so a reply added later is not added to its text. Excel 16.0 still shows the thread with every reply; Excel versions without threaded comments, which display the placeholder, would show the older text (not tested).
- **Threaded comments:** a thread on a cell that already has an ordinary note gets no placeholder, and Excel then shows the note, not the thread.
- **Threaded comments:** a thread removed from a model after a read (no API removes one) leaves its `tc=` placeholder note in `ws.comments`, and the placeholder is written back. Excel shows neither a note nor a thread on that cell, and a thread added there later gets no placeholder, because the cell has a note.
- **Threaded comments:** a cell holds one thread and a threaded comment text at most 32,767 UTF-16 code units, as in Excel. The API enforces both; a model built by hand that breaks either is written as given, and `validate()` reports it.
- **Threaded comments:** comments added faster than one per 10 ms are stamped 10 ms apart, so a burst of n replies ends up to n × 10 ms ahead of the clock (131,072 in one loop: about 22 minutes); a later comment follows the latest stamp.
- **Threaded comments:** `addThreadedComment` and `replyToComment` keep an index of a sheet's `threadedComments` array that they rebuild when the array or its length changes. After an entry of the array is replaced in place, or the array is edited without changing its length (a `splice` and then a `push`), they may not see a thread root the edit put on a cell, or a later timestamp, until the next rebuild; `validate()` still reports a second root on a cell.
- **Threaded comments:** `cloneSheet` gives a copied thread new random ids, and Excel shows replies with the same `dT` in id order, so the copy of a thread whose replies share a timestamp (Excel stamps replies added within 10 ms alike) can show its replies in another order. Giving a copy ids in the source thread's id order is planned for 1.10.0.
- **Tables and comments:** a note drawing read from a file that is not UTF-8 or not well-formed XML, or that binds the `v`, `o` or `x` prefix to another namespace, is written as it is with a warning, so notes added, removed or moved through the API are not drawn from it. A note drawing several sheets share takes the notes of the first of them with comments only.
- **Tables and comments:** note shapes added to a note drawing read from a file are numbered on from its highest shape number, and its `o:idmap` block is not extended, so an added shape can fall outside that block or repeat a number another sheet's generated note drawing uses. Excel 16.0 opened every such file tested.
- **Tables and comments:** `addTable` accepts a table name that holds a control character other than tab, line feed and carriage return (such as U+0008), and the writer drops the character, so the name in the file differs from the name in the model (`a` + U+0008 + `b` is written as `ab`); `validate()` does not report it. Refusing and reporting such a name is planned for 1.10.0.
- **Tables and comments:** `addTable` does not write the table's header row, and over header cells that hold no text it gives a file Excel refuses to open; set each header cell to its column name. Writing the column names into empty header cells is planned for 1.10.0.
- **Drawings and images:** preserved sheet relationships (drawings, VML drawings with form controls or header and footer pictures) are keyed by the sheet's position, and `removeSheet`, `moveSheet` and `cloneSheet` with an insert index do not re-key them, so after such a call a preserved drawing belongs to the sheet now at its old position.
- **Drawings and images:** a form control read from a file works after a round trip through its VML drawing, but the sheet's `<controls>` element is not kept, so Excel also loads the control's DrawingML fallback shape as a hidden shape.
- **Drawings and images:** pictures added with `addImage` are named `Barcode N` in the drawing.
- **Tables and comments:** a cell formula inside a table written in the `@` shorthand (`[@Qty]*[@Price]`) opens, but Excel reads it as `#REF!`; the API neither refuses nor rewrites it, and `addTable` refuses the shorthand in a table definition without rewriting it. Rewriting the shorthand into the form Excel writes is planned for 1.6.0.
- **Formula engine:** a formula that uses a table or defined name holding a backslash, a question mark or a non-ASCII symbol (`a\b`, `a?b`, `Ventes€`) is not parsed by the formula engine: `rewriteFormula` and `expandSharedFormula` return it unchanged. Accepting every name character Excel accepts is planned for 1.6.0.
- **Workbook and worksheet API:** `cloneSheet` renames a table in a formula the formula engine cannot read by masking the table names, so a formula that names a renamed table and also holds another name the engine cannot read (a defined name such as `\rate` or `a?b` outside a structured reference) keeps naming the source table in the copy.
- **Workbook and worksheet API:** `cloneSheet` renames structured references only, so a bare table name used as an operand in the copy (`ROWS(Table1)`) keeps naming the source table, as Excel's own sheet copy (Sheet.Copy, probed with Excel 365 on 2026-11-13) keeps it. Unlike Excel's copy, `cloneSheet` copies no defined names: Excel gives the copy its own sheet-scoped copies of the source sheet's sheet-scoped names and of the workbook names that refer to the sheet. Copying them is planned for 1.6.0.
- **Workbook and worksheet API:** `renameSheet` rewrites defined names, print areas and print titles only: cell formulas, chart series references, pivot cache worksheet sources, data-validation and conditional-format formulas and internal hyperlink locations that name the sheet keep the old name, so Excel then shows `#REF!`, cannot refresh the pivot table (its source becomes a sheet of another file) or follows a broken link. A defined-name value with a sheet-qualified defined name (`Sheet1!myName`) or a workbook-level external name (`[1]!srcName`) is left unchanged as a whole, because the formula tokenizer rejects it. Rewriting every part that names the sheet is planned for 1.6.0.
- **Workbook and worksheet API:** the children of a shared-formula master follow the master: replacing the master's formula text through the API changes the formula of every child that keeps its group on write, and clearing the master's formula writes a child without text of its own with its cached value alone (empty when it holds none) and a child that carries text of its own as a plain formula of that text. Groups are not re-homed onto another master; that is planned for 1.6.0. A shared-formula child that precedes its master in row order, and two masters on one `sharedIndex`, are written as given, and Excel refuses the file; `validate()` does not report them. A master whose `formulaRef` is blank or not a range (`' '`, `ZZZ!!`), or whose formula text is only U+200B, U+FEFF or `=` signs and spaces (`==`, `' = '`), is also written as a master as given, and `validate()` does not report it either. New formula text on a child gives that child a plain formula of its own (its shared keys are removed), so it keeps that formula whatever happens to the master.
- **Workbook and worksheet API:** `addNamedRange` refuses some defined names Excel 365 takes, planned for 1.6.0: a symbol (`a€b`, `a·b`, `a°b`, `a±b`, `a×b`, `a§b`), a number character that is not a decimal digit (`a²b`, `a½b`, `aⅫb`, and `²` or `Ⅻ` first), an emoji (`a😀b`, `a❤️b`, a ZWJ sequence, a skin-tone modifier), a soft hyphen (U+00AD), a zero-width non-joiner or joiner inside a word (Persian `می‌خواهم`, Devanagari `क्‍ष`), and a Thai mark as the first character (U+0E34); `addTable` likewise refuses a table name that starts with a Thai mark, which Excel opens. `validate()` does not report every defined name Excel refuses: a `:` elsewhere than between two name characters (`ab:`), a leading non-letter such as `€a`, or a no-break space.
- **Workbook and worksheet API:** the R1C1 name rule of `addNamedRange`, `addTable` and `validate()` was checked against English-language Excel only. An Excel whose R1C1 letters differ from `R` and `C` may save a defined name such as `R1x` or `C3PO`, which `validate()` then reports (not tested).
- **Workbook and worksheet API:** `addSheet`, `addTable` and `addNamedRange` compute one name key per call, but still read every stored sheet, table or defined name once per call (an identity and a string comparison), so building many of them takes time quadratic in their number, with a small constant: 10,000 `addSheet` calls take 1,357 ms, 50,000 `addTable` calls 4,066 ms, 50,000 `addNamedRange` calls 3,373 ms, and 4,000 `addNamedRange` calls with 255-character names of combining marks 127 ms (Node v26.13.0, medians of 3, measured on 2026-11-13). A removal other than of the last name, a reorder of the list, or the first check on a workbook just read makes the next check rebuild a key index of all names: 2,000 alternating removals from the head and additions on 10,000 defined names take 2.3 s, and the first check on a workbook of 1,000,000 defined names takes 0.8 s and keeps about 150 MB while the workbook lives (measured on 2026-11-13). Removing the scan and the rebuilds is planned for 1.6.0.
- **Workbook and worksheet API:** `validate()` compares table and defined names ignoring case only, not canonical equivalence, so it does not report a table `café` (U+00E9) beside a defined name or table `cafe` + U+0301, which Excel refuses, and it does not report a table or defined name that starts with a combining mark (U+0301 + `abc`, U+093F + `x`), which Excel refuses for some scripts; `addTable` and `addNamedRange` refuse all of these. `validate()` and `repair()` also compare sheet names ignoring case only, so sheets `café` (U+00E9) and `cafe` + U+0301 in a hand-built model or a crafted file, which `addSheet` refuses and Excel does not open, are neither reported nor renamed, nor are two sheets that differ only in the Greek final sigma (U+03C3 beside U+03C2, `ΑΣ` beside `ασ`), which Excel does not open either; and `validate()` finds the table a `[@...]` names ignoring case only, so it reports as the `@` shorthand a reference that names its table in another normal form (`Cafe` + U+0301 + `[@Home]` for a column `@Home` of table `Café`), which `addTable` accepts and Excel opens. These checks are planned for 1.6.0.
- **Workbook and worksheet API:** `addSheet`, `renameSheet`, the `Worksheet.name` setter, `cloneSheet`, `StreamingXlsxWriter.startSheet`, `addTable` and `addNamedRange` compare names ignoring case (with the Greek final sigma folded) and canonical equivalence only, and `validate()` ignoring case only (see above), because JavaScript has no full case-folding primitive. None of them finds a pair Excel treats as one beyond that, such as `Straße` and `STRASSE`, U+FB01 + `x` and `fix`, or U+03F5 and U+03B5: Excel 365 (build 20527, probed on 2026-11-13) refuses a file with two such sheets, two such tables, or such a table and defined name, and keeps one of two such defined names. Comparing names as Excel does is planned for 1.6.0.
- **Workbook and worksheet API:** canonical equivalence also takes a Hangul syllable and its conjoining jamo as one name (U+D55C beside U+1112 U+1161 U+11AB), so `addSheet`, `renameSheet`, the `Worksheet.name` setter and `cloneSheet` refuse the second as "already exists" (and `StreamingXlsxWriter.startSheet` as a duplicate), though Excel opens a file with both as sheet names and its own rename accepts the second; `addTable` and `addNamedRange` refuse the second as a table or defined name too, though Excel keeps two such defined names apart and opens a file with two such tables (it then keeps one table). The lower case of the comparison also takes as one name some pairs Excel opens as two sheets, which 1.2.1 accepted: Cherokee U+13A0 and U+AB70, Georgian U+10D0 and U+1C90, Deseret U+10400 and U+10428, Adlam U+1E900 and U+1E922, Osage U+104B0 and U+104D8, and Greek U+03F4 beside U+03B8. `cloneSheet` of a sheet that holds two tables named by such a Hangul pair (a file only another tool writes; Excel's own copy of it fails) points both tables' references in the copy at one of the copied tables. Comparing names as Excel does is planned for 1.6.0.
- **Workbook and worksheet API:** `renameSheet` matches a sheet prefix in a defined name ignoring case only (with the Greek final sigma folded), as Excel 365 does: a prefix spelled in another normal form of the sheet name (`cafe` + U+0301 + `!$A$1` for a sheet `café` with U+00E9) is kept, and Excel itself reads such a prefix as a reference into another workbook.
- **Workbook and worksheet API:** Cherokee and Georgian letters in either case are taken as one letter (U+13A0 with U+AB70, Georgian Mtavruli U+1C90 with Mkhedruli U+10D0), where Excel 365 keeps them apart (build 20527, probed on 2026-11-14): `renameSheet` rewrites a prefix spelled in the other case, which Excel keeps, and `addSheet`, `renameSheet`, `cloneSheet` and `StreamingXlsxWriter.startSheet` refuse a name that differs from another only so, which Excel accepts.
- **Streaming writer:** `StreamingXlsxWriter.startSheet` also refuses as a duplicate a name that differs from an earlier one only in one of 20 letters whose case pairs are new in Unicode 18 (such as U+A7DD beside U+0277), which `addSheet` accepts: the WASM core lower-cases with Rust's Unicode 18 tables (`char::UNICODE_VERSION` 18.0.0 in nightly-2026-11-14) and Node 26.13.0's `toLowerCase` follows Unicode 17.0 (ICU 78.3), where these 20 capital letters are not assigned (every code point compared on 2026-11-14).
- **Workbook and worksheet API:** `moveSheet` and `removeSheet` leave a 3-D span in a defined name as text, where Excel's own move rewrites it: after `moveSheet(2, 0)` on sheets `Sheet1`, `Sheet2`, `Sheet3`, a name holding `Sheet1:Sheet3!$A$2` keeps that text, which Excel then reads as `Sheet3:Sheet1` without `Sheet2` (Excel's move stores `Sheet1:Sheet2!$A$2`), and after `removeSheet('Sheet3')` the span still names `Sheet3`. Sheet-scoped names are remapped. Rewriting spans on move and remove is planned for 1.6.0.
- **Worksheets:** only the first `<sheetView>` of a sheet is kept on read and write, so a workbook saved with more than one window on a sheet (View > New Window in Excel) loses the other windows' selection and scroll position, and their `workbookViewId` entries in `xl/workbook.xml` no longer name a sheet view; Excel still opens the file with every window, as with 1.2.1. Keeping every sheet view is planned for 1.10.0.
- **Worksheets:** an auto filter keeps its value lists and custom filters through a read and a write, but its colour, icon, top-ten, dynamic (above-average and date-period) and date-group filters and its `sortState` are dropped, so Excel shows those columns' filters off in the written file, as with 1.2.1. Keeping them is planned for 1.4.0.
- **Worksheets:** an unprefixed name inside a kept worksheet `<ext>` takes the default namespace of the sheet it is written into: a default namespace declared on the `<worksheet>` root or on `<extLst>` is not declared on the `<ext>`. Declaring it there is planned for 1.4.0.
- **Reading:** a cell of thousands of repeated characters can compress past the default `maxCompressionRatio` of 100: an Excel-saved cell of 32,767 copies of one character gives a 9 KB file whose `xl/sharedStrings.xml` deflates past 100:1, so the default read fails with `SECURITY`, as in 1.2.1. Raise the ratio for files you trust (`readBuffer(bytes, { limits: { maxCompressionRatio: 10_000 } })` reads it).
- **Reading:** each workbook-level field (the styles, the shared strings and the defined names among them) and each sheet's charts, pivot tables, threaded comments, slicers and timelines are serialized whole into one temporary string before the read checks the JSON length, and a control character takes 6 bytes of JSON, so one such field of control characters can still trap the WebAssembly build (`RuntimeError: unreachable`): a number format code from 180 MB of XML (a 1,868,971-byte package; from 100 to 179 MB the read fails with `SIZE_LIMIT`), a defined name's value from 180 MB (1,869,023 bytes) and one shared string from 195 MB (2,024,414 bytes). 1.2.1 traps on them sooner, from 158 MB, 158 MB and 90 MB (and fails from 100 MB of a number format code or defined name with a JavaScript string-length error). Measured on 2026-11-13. Writing these fields one element at a time is planned for 1.4.0.
- **Reading:** through the WebAssembly build, any read that builds hundreds of MB of output from small allocations reads in time that grows faster than its output, because the WebAssembly memory grows in small steps and each step costs time in proportion to the memory already held: a shared string table of millions of rich text entries, and kept worksheet extensions that inherit many namespace declarations. One-run entries (`<si><r></r></si>`) take 0.25 s for 500,000, 0.63 s for 1,000,000, 1.9 s for 2,000,000 and 3.5 s for 2,800,000 (a 475 KB package, 797 MiB of WebAssembly memory); 1,000,000 entries of two runs take 2.7 s; plain entries stay linear (2,800,000 in 0.53 s). The native Rust crate reads the same shape in linear time. 1.2.1 has the same behaviour and is slower: 2,800,000 one-run entries take 7.9 s and 968 MiB on the same machine. The table's size limit still ends such a flood: 2,917,776 one-run entries fail with `SIZE_LIMIT`. Measured on 2026-11-13 with Node 26.13 on Windows 11. A 1,965,765-byte package whose `<worksheet>` root declares 1,000 prefixes used by each of 11,500 kept `<ext>` reads 343 MB of JSON in about 3.7 s, where the same JSON from `<ext>` elements that declare the prefixes themselves takes 3.0 s and the native read 2.0 s, and in 10.9 to 15.1 s in an instance whose memory had already grown by 1.5 GiB (4.1 to 4.5 s without that growth in the same runs, on a host shared with other work) (measured on 2026-11-14 with Node 26.13 on Windows 11, release builds); the JSON length limit bounds it, since every inserted declaration is counted against `maxJsonLength`. Growing the memory in larger steps is planned for 1.4.0.
- **Workbook and worksheet API:** the lookups by name match a name exactly, while the add methods refuse a name equal to another ignoring case and canonical equivalence: `getSheet`, `removeSheet`, `hideSheet`, `unhideSheet`, the sheet-name argument of `renameSheet` and `addImage`, `getTable`, `removeTable`, `getNamedRange` and `removeNamedRange`. So `getSheet('DATA')` does not find `Data` although `addSheet('DATA')` is refused as taken, `getNamedRange('sales')` does not find `Sales`, and `cafe` + U+0301 does not find `café` (U+00E9). Matching names as the add methods compare them is planned for 1.6.0.
- **Workbook and worksheet API:** `getSheet` answers from an index of sheet names that only the API keeps up to date: after a sheet's name is changed by a direct write to the object `toJSON()` hands out, `getSheet` finds the sheet by its old name and not by its new one, while `addSheet` already refuses the new one as taken. Change sheet names through `renameSheet` or the `Worksheet.name` setter. Answering from the sheet data is planned for 1.6.0.
- **Streaming writer:** `StreamingXlsxWriter` has no row-height option: a streamed row's height follows the font size of its style, as Excel sizes it. A row-height option is planned for 1.4.0.
- **Utilities and CLI:** `modern-xlsx convert in.xlsx out.csv` writes JSON: the output format comes from `--format` (default `json`), not from the file extension. Inferring it from the extension is planned for 1.10.0.
- **Worksheets:** cell text that contains a literal `_xHHHH_` sequence (such as `_x0041_`) is written as it is, and Excel decodes it (`_x0041_` shows as `A`). Encoding such text on write (as `_x005F_x0041_`) is planned for 1.5.0.
- **Workbook parts:** `WorkbookProtectionData.workbookPassword` and `revisionsPassword` hold the legacy hash a file stores but are written as given, unchecked, unlike a sheet protection `password`; with a plain-text `workbookPassword` Excel unprotects the workbook with any password.
- **Writing:** text holding a lone UTF-16 surrogate makes `toBuffer()` fail with a `JSON` error, and cell text longer than 32,767 characters, Excel's per-cell limit, is written without an error or a warning. Writing U+FFFD for a lone surrogate and reporting over-long text are planned for 1.4.0.
- **Writing:** a `preservedEntries` name set in the model by hand (a read of a package never gives one) is written as given: a name that is percent-encoded, holds a backslash or ends in a dot or a space gives a file Excel refuses to open, and one that starts with `/` or `../` gives a file whose read fails with `SECURITY`. Skipping such names with a warning is planned for 1.4.0.
